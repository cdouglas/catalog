# C19. A sort order replaced after another writer renamed its column fails with an NPE

| | |
|---|---|
| **Affects** | Iceberg 1.12.0, and `main` at `834441b96` (2026-10-21), on every catalog but REST, whose server binds the order by field id. |
| **Upstream** | Not reported (searched apache/iceberg issues and PRs, 2026-10-20). |
| **Fix** | [`7e4517f`](https://github.com/cdouglas/iceberg/commit/7e4517f5d6acdccfcb2c60ae070e56d09ffba9a5) on [`core-fixes`](https://github.com/cdouglas/iceberg/tree/core-fixes), "Core: Bind a replaced sort order to the schema each attempt commits on". 2 files, +35 -1. Cherry-picks cleanly onto `main` at `834441b96`. |
| **Found by** | fileio-catalog's review of Iceberg's commit retry paths for state read before an attempt, 2026-10-20. Reproduced in `TestSortOrder`. |

## Summary

`table.replaceSortOrder().asc("data")` binds its fields to the table's
schema when it is created. If another writer renames `data` before the
order commits, the commit fails with a `NullPointerException`. Run in
either order, the two changes end with the table sorted by the renamed
column, or the sort order failing with "Cannot find field 'data'".

## Reproduction

```java
ReplaceSortOrder order = table.replaceSortOrder().asc("data");

catalog.loadTable(ID).updateSchema().renameColumn("data", "payload").commit();

order.commit();
// NullPointerException: Cannot invoke "Types$NestedField.fieldId()" because the return value
// of "Schema.findField(String)" is null
```

## Cause

`BaseReplaceSortOrder` builds the order against the schema it has when
it is created
([BaseReplaceSortOrder.java#L42](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/BaseReplaceSortOrder.java#L42)),
and each attempt passes that order to the refreshed metadata
([#L63](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/BaseReplaceSortOrder.java#L63)).
The metadata builder rebuilds it
([TableMetadata.java#L1739](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/TableMetadata.java#L1739)):
it looks each field's name up in the order's schema, the old one, and
then finds that name in the current schema
([#L826-L831](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/TableMetadata.java#L826-L831)),
which no longer has it. A REST client sends the order unbound, with
field ids, and the server binds it to its schema by id, so it sorts by
the renamed column.

## Impact

The sort order change fails with an exception that says nothing of the
rename. The table is unchanged; running the change again works.

## Fix

Each attempt binds the order by field id to the schema of the metadata
it commits on, as a REST server does:

```java
// bound by field id to the schema this attempt commits on: another writer may have
// renamed a column since the order was built
SortOrder newOrder = apply().toUnbound().bind(base.schema());
```

The order then sorts by the renamed column, as when the rename follows
the order. A column dropped in between fails the bind with
`ValidationException` ("Cannot find source column for sort field"), as
before.

## Tests

In `TestSortOrder`, on every format version:

- `testReplaceSortOrderAfterConcurrentRename`: the reproduction. The
  table is sorted by `payload`.
- `testReplaceSortOrderAfterConcurrentDrop`: a dropped column still
  fails cleanly. It passes without the fix too.

The 4 rename cases fail without the fix. With it, `TestSortOrder`,
`TestReplaceTransaction`, `TestTransaction`, `TestTableMetadata`, the
catalog and in-memory catalog tests, and the full `iceberg-core` test
task pass.

## Before a PR

- **Succeed or fail.** Both serial orders are possible outcomes; the fix
  picks the one REST already gives. A reviewer may prefer failing with
  `ValidationException`, a smaller change in `freshSortOrder`.

## In fileio-catalog

No workaround. `TableScript` replaces sort orders and renames columns,
but not through a handle that missed the rename, outside the
differential property. The canary is
`TestIcebergCoreIssues.aSortOrderReplacedAfterARenameDoesNotFail`. It
asserts only that the commit does not fail with a
`NullPointerException`.
