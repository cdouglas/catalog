## Summary

`TableMetadata.Builder.rewriteSnapshotsInternal`, which `removeSnapshots`
calls, sizes the list of the snapshots it keeps as the snapshots it has
less the ids it removes. A removal applied to newer metadata than it was
computed on can name snapshots that are already gone. A REST server
applies a client's `remove-snapshots` update to the table's current
metadata, with no requirement on the snapshots it names (the client's
`UpdateRequirements` derives none, C22), so when another expiry removed
most of the same snapshots first, the update names more snapshots than
the table has. The size is negative, and Guava's
`Lists.newArrayListWithExpectedSize` throws `IllegalArgumentException`
("arraySize cannot be negative"), which the server returns as a bad
request. Removing a snapshot that is gone changes nothing: the update
should apply, as a no-op for those ids.

## Reproduction

`TestIcebergCoreIssues.aRemovalOfMoreSnapshotsThanTheTableHasApplies`
(fileio-catalog) on an `InMemoryCatalog`: a table of three snapshots; an
expiry that keeps one; then `CatalogHandlers.updateTable`, as a REST
server, applies a `RemoveSnapshots` update of the two older snapshots,
computed on the table before that expiry:

| Case | 1.12.0 | Fixed |
|---|---|---|
| One update removes 2 ids from a table of 1 snapshot | IllegalArgumentException | applies; the table keeps its snapshot |
| One update per id (Java's client since 1.9.1), on a table of 1 snapshot | applies | applies |
| One update of 1 id, on a table with no snapshots left | IllegalArgumentException | applies |

Through Iceberg's own REST client the race does not reproduce: the
builder records one update per snapshot it removes, and a server applies
each with one id, below zero only on a table left with no snapshots (a
table whose expiry may remove every snapshot: one with no refs).

## Cause

`rewriteSnapshotsInternal` sizes `retainedSnapshots` with
`snapshots.size() - idsToRemove.size()`, assuming every id is one of the
table's snapshots. That holds for an expiry applied to the metadata it
was computed on (`RemoveSnapshots.internalApply`), not for its update
replayed on newer metadata.

## Impact

- A REST catalog's expiry, from a client that sends one update with every
  id (Iceberg 1.9.0's; one that returns to #12670's bulk update), fails
  with a bad request when another expiry of the same table removed most
  of the same snapshots first: concurrent maintenance jobs on one table.
  The table is as the other expiry left it; this one's removal of what
  remains of its choice is lost, and a retry would recompute it.
- From Iceberg's own client since 1.9.1, only on a table with no
  snapshots left.
- Nothing is corrupted: the update fails as a whole, before it changes
  anything.

## Fix

Size the list at zero or more (`Math.max(0, ...)`). The loop already
skips ids the table lacks.

## Tests

`TestTableMetadata.testRemovingMoreSnapshotsThanTheTableHas`: a
`RemoveSnapshots` update of two snapshots another writer removed, applied
to the metadata that remains, and `removeSnapshots` with the same ids,
both leave the table's one snapshot. It fails on `core-fixes` without the
fix with `IllegalArgumentException`; `TestTableMetadata` (72 tests) passes
with it.

## Before a PR

One line; the question for review is whether a server should apply a
removal of snapshots that are gone as a no-op (as it does a removal of
one id that is gone, while the table has snapshots) or fail it as a
conflict. A no-op matches what the update means (the snapshots are not in
the table after it), and #13647's comments expect bulk updates to return,
which makes the race reachable from Java's client again. C22's fix
(a removal fails while a ref points to one of its snapshots) sits in the
same path on the fork.

## In fileio-catalog

fileio-catalog's own expiry record (`InlineDeltaCodec.RemoveSnapshotsUpdate`)
carries every id, and an expiry merged onto a changed table (errata D17's
fix, `ConcernVectorEncoding`) can name snapshots another expiry removed.
Native replay skips them; the replay check
(`-Dfileio.catalog.replay.check`, `NativeDelta.reference`) applies the
record through Iceberg's builder, and removes only the snapshots the table
has, so it does not depend on this fix. The canary applies a bulk update
as a REST server does. catalog-bench's Polaris clients are Iceberg's Java
client (one update per snapshot), so its runs meet C30 only on a table
left with no snapshots, which none of its workloads makes.
