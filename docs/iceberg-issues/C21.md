# C21. Ref and spec removals applied to newer metadata lose a concurrent commit or remove a spec in use

| | |
|---|---|
| **Affects** | Iceberg 1.12.0, and `main` at `834441b96` (2026-10-21), on catalogs that apply a commit's updates to the table's current metadata, checked only by the requirements `UpdateRequirements` derives: REST catalogs whose server uses `CatalogHandlers`, and fileio-catalog's catalog transactions. Catalogs that commit whole metadata, such as `InMemoryCatalog`, are not affected. |
| **Upstream** | Not reported (searched apache/iceberg issues and PRs, 2026-10-20). PR [#10755](https://github.com/apache/iceberg/pull/10755), in 1.8.0, added the spec removal and its requirements, excluding main; its review gives no reason. |
| **Fix** | [`517c1c4`](https://github.com/cdouglas/iceberg/commit/517c1c4a882f0b9613093947d5ed2bb92c35bac1) on [`core-fixes`](https://github.com/cdouglas/iceberg/tree/core-fixes), "Core: Require the refs that ref and spec removals depend on". 2 files, +150 -9. Cherry-picks cleanly onto `main` at `834441b96`. |
| **Found by** | fileio-catalog's review of Iceberg's commit retry paths for state read before an attempt, 2026-10-20. Reproduced through `RESTCatalogAdapter` and `CatalogHandlers`, on `InMemoryCatalog`. |

## Summary

A REST server applies a client's updates to the table's current
metadata, which may be newer than the metadata the client computed them
on. It first checks the requirements the client derived with
`UpdateRequirements`. Two removals depend on refs that their
requirements do not name:

- **A ref removal requires nothing.** `renameBranch("b", "c")` sends the
  removal of `b` and the creation of `c` at the snapshot the client saw
  `b` at. If another writer committed to `b` in between, the server
  removes `b` with that commit on it, and creates `c` where `b` was: the
  commit is on no branch. An expiry that removes an aged-out ref has the
  same gap.
- **A spec or schema removal requires every branch but main.**
  `cleanExpiredMetadata(true)` removes the specs and schemas that no
  snapshot it keeps uses. If a commit to main lands first and adds
  files of such a spec, the server removes the spec anyway, and every
  scan of the table fails. A table's first commit creates main, which
  the requirements can't name at all.

Run in either order, both pairs end with the commit kept (rename after
it, or spec kept), or with the second operation failing.

## Reproduction

The updates a client computes on `base`, applied by a REST server after
another writer's commit:

```java
table.manageSnapshots().createBranch("b", s1).commit();
TableMetadata base = ops.current();
TableMetadata renamed = TableMetadata.buildFrom(base)
    .removeRef("b").setRef("c", SnapshotRef.branchBuilder(s1).build()).build();

catalog.loadTable(ID).newFastAppend().appendFile(FILE_B).toBranch("b").commit();   // s2 on b

CatalogHandlers.updateTable(catalog, ID, UpdateTableRequest.create(ID,
    UpdateRequirements.forUpdateTable(base, renamed.changes()), renamed.changes()));
// succeeds: no ref points to s2
```

```java
client.updateSpec().addField("id").commit();               // spec 1 is the default
// another writer appends a file of spec 0 to main, then the client's expiry lands
client.expireSnapshots().cleanExpiredMetadata(true).commit();
server.specs();                                            // {1}
server.newScan().planFiles();
// NullPointerException in ManifestEvaluator: "spec" is null
```

## Cause

`UpdateRequirements` derives no requirement from a `RemoveSnapshotRef`
([UpdateRequirements.java#L96-L112](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/UpdateRequirements.java#L96-L112)),
though it requires a ref that is set to be unchanged
([#L117-L129](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/UpdateRequirements.java#L117-L129)).
`renameBranch` removes the old ref and sets the new one
([UpdateSnapshotReferencesOperation.java#L86-L97](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/UpdateSnapshotReferencesOperation.java#L86-L97)).
A spec or schema removal requires the default spec or current schema,
and every branch but main, to be unchanged
([UpdateRequirements.java#L168-L180](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/UpdateRequirements.java#L168-L180),
[#L200-L210](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/UpdateRequirements.java#L200-L210)),
"so that old specs won't be written". A commit to main may add files of
any spec the table has, and a writer whose job started before a
partition change does.

## Impact

- A branch rename that races a commit to the branch loses the commit
  from every ref. Both writers see success.
- An expiry with `clean_expired_metadata` that races a commit of old-spec
  files to main leaves a table no engine can scan, and no API adds a
  spec back under its old id. A rollback past the commit recovers it.

## Fix

```java
private void update(MetadataUpdate.RemoveSnapshotRef removeRef) {
  // require that the ref is unchanged from the base: removing a ref that another writer has
  // moved since would drop the snapshots committed to it
  requireRefNotChanged(removeRef.name());
}
```

`requireRefNotChanged` is the existing check for a ref that is set,
moved into a method. Spec and schema removals now also require main to
be unchanged, or still absent if the client saw none.

## Tests

In `TestUpdateRequirements`:

- `removeSnapshotRef` and `removeSnapshotRefFailure`;
- `removePartitionSpecsWithMainChangedFailure`,
  `removePartitionSpecsWithMainCreatedFailure` and
  `removeSchemasWithMainChangedFailure`;
- upstream's `removePartitionSpec`, `removeSchemas` and their `WithBranch`
  variants now also expect the requirement on main.

All 9 new and changed tests fail without the fix.
With it, `TestUpdateRequirements`, the REST, catalog and in-memory
catalog tests, `TestSnapshotManager`, `TestRemoveSnapshots` and the full
`iceberg-core` test task pass.

## Before a PR

- **More conflicts.** An expiry that cleans expired metadata now
  conflicts with every commit to main that lands while it runs. The
  client retries it (`RemoveSnapshots` recomputes what it removes on
  each attempt since C10), but a busy table may exhaust its retries.
  Upstream may have excluded main for this reason; the review of #10755
  doesn't say. A server-side check of what the new snapshots use would
  avoid the conflicts, at the cost of reading manifest lists.
- **New branches** are still a gap: a branch another writer creates
  after the client's read, with commits of an old spec, is in no
  requirement. Only a server-side check closes that.
- **The other order**, an append landing after the spec's removal, is
  C11's REST note and remains open.

## In fileio-catalog

`FileIOCatalog.commitTransaction` checks a catalog transaction's table
commits by these requirements, so it had both gaps. Its Bug 69 check
already covers the append that lands after the removal. The canary is
`TestIcebergCoreIssues.removalsAppliedToNewerMetadataRequireTheirRefs`,
which applies stale updates through `CatalogHandlers`, as a REST server
would. It asserts only that the branch commit stays on a ref and the
spec stays.
