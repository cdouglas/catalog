# C5. Rewriting manifests fails on a table without a current snapshot

| | |
|---|---|
| **Affects** | Iceberg 1.10.1 and 1.12.0, and `main` at `524fe9e` (2026-10-16). The files the fix changes have not changed on `main` between `524fe9e` and `9bbee07` (2026-10-18). |
| **Upstream** | Not reported (searched apache/iceberg issues and PRs, 2026-10-16). |
| **Fix** | [`f723a52`](https://github.com/cdouglas/iceberg/commit/f723a52a663326cf5fd80d763df1a2d4988dc1f7) on [`core-fixes`](https://github.com/cdouglas/iceberg/tree/core-fixes), "Core: Rewrite the manifests of a table without a current snapshot". 2 files, +34/−3. Cherry-picks cleanly onto `main` at `9bbee07`. |
| **Found by** | fileio-catalog's `TestCatalogFaultProperties`, through a replace transaction racing a manifest rewrite. |

## Summary

`table.rewriteManifests()...commit()` throws a `NullPointerException` when
the table has no current snapshot. Either the table never had one, or a
replace transaction left it with none after the rewrite began.

## Reproduction

```java
Table table = catalog.createTable(ID, SCHEMA);
table.rewriteManifests().clusterBy(file -> "all").commit();   // NullPointerException

// or, through a concurrent replace:
table.newFastAppend().appendFile(file("a")).commit();
RewriteManifests rewrite = table.rewriteManifests().clusterBy(file -> "all");
catalog.buildTable(ID, SCHEMA).replaceTransaction().commitTransaction(); // no current snapshot
rewrite.commit();                                               // NullPointerException
```

The message is `Cannot invoke "Snapshot.allManifests(FileIO)" because the
return value of "TableMetadata.currentSnapshot()" is null`.

## Cause

`BaseRewriteManifests.apply(base, snapshot)` dereferences
`base.currentSnapshot()`
([BaseRewriteManifests.java#L171](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/BaseRewriteManifests.java#L171)).
It does so again in `validateDeletedManifests`. Other snapshot producers
treat a missing parent snapshot as one without manifests.

## Impact

The rewrite fails with an unexpected exception instead of a result. The
Spark `RewriteManifests` action doesn't call the core API on a table
without a snapshot. Direct API users, and rewrites that race a replace
transaction, hit it.

## Fix

`apply` uses the parent snapshot it is given (`snapshot`, the head of
`main`; the rewrite doesn't support branches). When there is none, it
treats the table as having no manifests:

```java
List<ManifestFile> currentManifests =
    snapshot != null ? snapshot.allManifests(ops().io()) : ImmutableList.of();
```

A rewrite that deletes a manifest still fails, with "Deleted manifest ...
could not be found in the latest snapshot null". A rewrite that adds a
manifest with live files still fails the file-count check.

**What it commits:** a rewrite of a table without a current snapshot now
commits a `replace` snapshot with no manifests and no parent. That is what
the rewrite already does when it has nothing to rewrite on a table with a
snapshot: it commits a snapshot that keeps every manifest. An empty append
behaves the same way.

## Tests

- `TestRewriteManifests.testRewriteManifestsWithoutSnapshot`
- `TestRewriteManifests.testRewriteManifestsWithConcurrentReplace`, where
  the replace runs after the rewrite was created.

Both are checked on every format version. All 8 cases fail on 1.12.0 with
the `NullPointerException`.

## Before a PR

- **The main open question is the semantics.** The alternative is to
  commit nothing: a rewrite of nothing changes nothing. But
  `SnapshotProducer` has no way for an operation to skip its commit, and
  the decision would have to be made again on every retry. A
  check-then-commit override would still race a concurrent replace, and
  then commit an empty snapshot anyway. Reviewers may prefer the no-op:
  the Spark `RewriteManifests` action already commits nothing, returning
  an empty result, when there is no snapshot or nothing to rewrite. If
  so, it needs a small hook in `SnapshotProducer.commit`.
- **Reads the parameter:** the fix reads the `snapshot` parameter instead
  of `base.currentSnapshot()`. They are the same, since `RewriteManifests`
  rejects `toBranch`.
- **Overlaps C4:** C4's fix changes the same class (its `specsById` field),
  but the two commits are independent.

## In fileio-catalog

The workarounds, in `TestCatalogFaultProperties`: it didn't generate a
rewrite for a table its model said had no snapshot, and its
`rewriteManifests` op caught the exception from a concurrent replace.
[`63dd25e`](https://github.com/cdouglas/catalog/commit/63dd25e95d4305f079565a38635d4630d574783a)
removed them, with the canary test. With the workarounds removed and
without the fix, the fuzzer finds C5 within 50 tries. A new canary,
`TestIcebergCoreIssues.aRewriteOfManifestsRunsOnATableWithoutASnapshot`,
asserts the bug is absent, in both cases.
