| | |

## Summary

A replace transaction (`replaceTransaction`, `createOrReplaceTransaction`)
builds its replacement metadata when it begins. The replacement keeps the
table's snapshot history. If another writer expires a snapshot before the
replace commits, the replace puts the expired snapshot back. The expiry
has already deleted that snapshot's manifest list. Reading the snapshot
then fails with `NotFoundException`, as do the `all_*` metadata tables,
time travel to it, and the file cleanup of later expiries, all of which
read every kept snapshot's manifest list.

## Reproduction

```java
Table table = catalog.createTable(ID, SCHEMA);
table.newFastAppend().appendFile(file("a")).commit();
long first = table.currentSnapshot().snapshotId();
table.newFastAppend().appendFile(file("b")).commit();

Transaction replace = catalog.buildTable(ID, SCHEMA).replaceTransaction();
replace.newFastAppend().appendFile(file("c")).commit();
catalog.loadTable(ID).expireSnapshots().expireSnapshotId(first).commit();
replace.commitTransaction();

Snapshot expired = catalog.loadTable(ID).snapshot(first);   // not null
expired.allManifests(table.io());                            // NotFoundException
```

## Cause

`BaseTransaction.commitReplaceTransaction` refreshes the table on each
attempt. It then commits the replacement it built at the start, whatever
the refreshed table holds
([BaseTransaction.java#L297-L328](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/BaseTransaction.java#L297-L328)).
The replacement comes from `TableMetadata.buildReplacement`
([TableMetadata.java#L718](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/TableMetadata.java#L718)),
which keeps every snapshot of the table at the start. Iceberg intends a
replace to win over concurrent changes (the code comment says so). But a
snapshot that an expiry removed, and whose files it deleted, can't
meaningfully come back.

## Impact

After a replace races an expiry, the table holds a snapshot without its
manifest list. Operations that read every snapshot's manifest list fail
until someone removes that snapshot by hand. A likely trigger is a
scheduled `expire_snapshots` running during a `CREATE OR REPLACE TABLE
... AS SELECT`.

## Fix

The fix records the snapshot ids the table had when the transaction
began. On a retry that finds the table changed, it removes from the
replacement the starting snapshots the refreshed table no longer has:

```java
Set<Long> removed = Sets.difference(startingSnapshotIds, snapshotIds(base));
if (!removed.isEmpty()) {
  this.current = TableMetadata.buildFrom(current).removeSnapshots(removed).build();
}
```

`TableMetadata.Builder.removeSnapshots` also drops refs that would be left
pointing at a removed snapshot. That covers a tag or branch whose snapshot
was expired after the ref was removed. Nothing else about the replace
changes: it still wins over other concurrent changes, including snapshots
added since.

## Tests

`TestReplaceTransaction.testReplaceTransactionWithConcurrentExpiry`, on
every format version. It runs the reproduction, and checks that the
expired snapshot stays gone, the other snapshot stays, and the replace's
data is current. All 4 cases fail on 1.12.0. With the fix, the transaction
and catalog suites (`TestReplaceTransaction`, `TestTransaction`, the
in-memory, JDBC and Hadoop `CatalogTests`; 812 tests) and the full
`iceberg-core` check pass.

## Before a PR

- **Coordinate with #16943.** That PR rebuilds the replacement on the
  refreshed metadata and replays the transaction's updates when the table
  changed. It falls back to today's behavior when the rebuilt schema, spec,
  sort order or format version would differ, or an update can't be
  replayed. This fix is much smaller, and also applies in those fallback
  cases. Options:
  - a comment on #16943 with this repro, asking that the fallback drop
    expired snapshots;
  - this as a small companion PR that #16943 can build on;
  - nothing, if #16943 lands and covers it.

  Check #16943's current state first; the description above is from
  2026-10-12.
- **Fuzzer coverage:** fileio-catalog's fuzzer didn't reproduce C3 again
  in about 9,800 tries without the fix, so its coverage of this case is
  weak. The core test above and fileio-catalog's canary (see "In
  fileio-catalog") are the evidence.

## In fileio-catalog

The workarounds, both in `TestCatalogFaultProperties`:

- It checked manifest lists only for snapshots a ref reaches.
- Its `REPLACE_TABLE` model put back every ref of the replacement. It now
  drops a ref whose snapshot was expired since the replace began. The
  model reads which snapshots the replace committed from
  `BaseTransaction.currentMetadata()`.

[`411f73c`](https://github.com/cdouglas/catalog/commit/411f73cd10fbade2a17f003ec618693beef1e0d5)
removed the workarounds, with the canary test. The fuzzer still models a
replace as winning over everything else (accepted behavior A1 in
`docs/ICEBERG_ISSUES.md`). A new canary,
`TestIcebergCoreIssues.aReplaceDoesNotBringBackASnapshotExpiredSinceItStarted`,
asserts the bug is absent.
