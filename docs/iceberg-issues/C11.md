# C11. An append commits files of a partition spec another writer removed

| | |
|---|---|
| **Affects** | Iceberg 1.12.0, and `main` at `3738f4a97` (2026-10-20), on every catalog. 1.8.0 added the spec removal (`ExpireSnapshots.cleanExpiredMetadata`). |
| **Upstream** | Not reported (searched apache/iceberg issues and PRs, 2026-10-20). PR [#10755](https://github.com/apache/iceberg/pull/10755), which added the removal, discussed commits that race it in the other order; the REST requirements it led to cover that order only (see "Before a PR"). |
| **Fix** | [`69e83ef`](https://github.com/cdouglas/iceberg/commit/69e83effcbc7c59ec1c2822c6af38605d445501f) on [`core-fixes`](https://github.com/cdouglas/iceberg/tree/core-fixes), "Core: Fail a commit of files whose partition spec was removed concurrently". 6 files, +181 -3. Cherry-picks cleanly onto `main` at `3738f4a97`. |
| **Found by** | fileio-catalog's `TestCatalogFaultProperties`, 2026-10-20, at try 26,798 of a 30,000-try run: a merge append through a handle loaded before another writer partitioned the table and expired with metadata cleanup failed with `NullPointerException: Cannot invoke "PartitionSpec.specId()" because "spec" is null`, with no fault injected. |

## Summary

An expiry that cleans expired metadata (`cleanExpiredMetadata(true)`)
removes the partition specs no remaining snapshot uses, other than the
default. A writer may have added files of such a spec to an append, a row
delta or another snapshot update that has not committed yet. The commit
then goes one of two ways:

- The spec was removed before the commit's attempt: the attempt looks the
  spec up in the refreshed metadata, finds nothing, and fails with a
  `NullPointerException` while writing the files' manifest.
- The spec was removed between two attempts: the first attempt wrote the
  manifest, and its commit failed on the expiry's. The retry reuses that
  manifest without looking the spec up, and commits it. The table now has
  a snapshot whose manifest names a spec the table does not have, and
  every scan of it fails with a `NullPointerException`.

The same holds for a manifest added with `appendManifest`, on the first
attempt too: it is committed as it is.

## Reproduction

```java
Table table = catalog.createTable(ID, SCHEMA);            // unpartitioned: spec 0
AppendFiles append = table.newFastAppend().appendFile(file("a"));   // a spec 0 file

Table other = catalog.loadTable(ID);                       // another writer
other.updateSpec().addField("id").commit();                // spec 1 is the default
other.expireSnapshots().cleanExpiredMetadata(true).commit();   // removes spec 0

append.commit();
// NullPointerException: Cannot invoke "org.apache.iceberg.PartitionSpec.specId()"
// because "spec" is null
```

With the expiry run just before the append's first commit instead (the
racing operations of C10's reproduction), the append commits:

```java
racingTable.newFastAppend().appendFile(file("a")).commit();   // succeeds
table.refresh();
table.specs().keySet();                                  // [1]
table.currentSnapshot().allManifests(io).get(0).partitionSpecId();   // 0
table.newScan().planFiles();
// NullPointerException: Cannot invoke "org.apache.iceberg.PartitionSpec.partitionType()"
// because "spec" is null
```

`newAppend()` (a merge append) behaves the same, and so does a row delta
that adds a delete file of the removed spec (format v2).

## Cause

`MergingSnapshotProducer.add` and `FastAppend.appendFile` check the file's
spec when the file is added, against the metadata the handle has then
([MergingSnapshotProducer.java#L240-L247](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/MergingSnapshotProducer.java#L240-L247)).
Each attempt of the commit refreshes first
([SnapshotProducer.java#L295-L296](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/SnapshotProducer.java#L295-L296)),
and writes the new files' manifests with the spec it looks up again, in
the refreshed metadata, without a check
([MergingSnapshotProducer.java#L1158](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/MergingSnapshotProducer.java#L1158),
[#L1197](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/MergingSnapshotProducer.java#L1197),
[FastAppend.java#L212](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/FastAppend.java#L212)).
A null spec reaches `ManifestWriter`.

Both producers keep the manifests an attempt wrote, and a retry reuses
them unless files were added in between
([MergingSnapshotProducer.java#L1148-L1154](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/MergingSnapshotProducer.java#L1148-L1154),
[FastAppend.java#L204-L210](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/FastAppend.java#L204-L210)).
Nothing checks a reused or appended manifest's spec against the metadata
the attempt commits on
([SnapshotProducer.java#L304](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/SnapshotProducer.java#L304)).

The expiry works out the specs to remove from the snapshots it retains
([RemoveSnapshots.java#L239-L265](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/RemoveSnapshots.java#L239-L265)),
so it keeps a spec that a commit before it used. It cannot see a commit
that is yet to come.

## Impact

A `CALL expire_snapshots(..., clean_expired_metadata => true)` that runs
while a writer is appending files of an old spec, such as a job started
before a partition change, can:

- fail the writer with a `NullPointerException`, which does not say what
  happened;
- or, when the expiry lands between the writer's attempts, commit the
  writer's files under a spec the table no longer has. The commit
  succeeds. After it, every scan of the table fails, as do, read from the
  code, later commits that read its manifests, such as a merge append or
  a delete. No API adds a spec back under its old id; a rollback to the
  snapshot before removes the bad one from the branch, and its files
  with it.

## Fix

The commit fails with `ValidationException`, which is not retried, when
the metadata it applies to no longer has the spec of a file or manifest
it adds:

- a new `SnapshotProducer.specForNewFiles(specId)` looks the spec up in
  that metadata and fails if it is gone. `FastAppend` and
  `MergingSnapshotProducer` use it where they write the manifests of new
  data files and of new delete files.
- `SnapshotProducer.apply()` checks that every manifest of the new
  snapshot has its spec in that metadata. This catches manifests written
  by an earlier attempt, and appended ones.

```java
List<ManifestFile> manifests = apply(base, parentSnapshot);

// a manifest written by an earlier attempt, or appended, may be of a spec removed since
for (ManifestFile manifest : manifests) {
  ValidationException.check(
      base.spec(manifest.partitionSpecId()) != null,
      "Cannot commit manifest %s: its partition spec %s was removed concurrently",
      manifest.path(),
      manifest.partitionSpecId());
}
```

Run after the expiry, the append's `add` would have failed ("Cannot find
partition spec"), so the failure is the outcome of a serial order.

## Tests

On every format version:

- `TestFastAppend.testAppendAfterConcurrentSpecRemoval`: the first
  reproduction. The commit fails with `ValidationException`, and the
  table has no snapshot.
- `TestFastAppend.testRetryAfterConcurrentSpecRemoval`: the second. The
  retry fails with `ValidationException` instead of committing.
- `TestFastAppend.testAppendManifestAfterConcurrentSpecRemoval`: an
  appended manifest of the removed spec.
- `TestMergeAppend.testAppendAfterConcurrentSpecRemoval` and
  `testRetryAfterConcurrentSpecRemoval`, on `main` and on a branch.
- `TestRowDelta.testAddDeletesAfterConcurrentSpecRemoval`, v2 on `main`
  and on a branch: a delete file of the removed spec. In v3 the row
  delta first fails to validate its deletion vector against history the
  expiry removed.

All 30 cases that run fail on 1.12.0: those that remove the spec before
the commit with a `NullPointerException`, the others by committing. With
the fix, the three test classes (752 cases) and the full `iceberg-core`
test task pass.

## Before a PR

- **REST.** The check runs where the commit is applied: on the client,
  for a REST catalog. An expiry that commits between the client's
  attempt and the server's commit is not caught there. An append's
  update requirements assert only that its branch is unchanged, and an
  expiry never moves a branch's head, so the server would commit the
  manifests of the removed spec (read from the code, not tested).
  `UpdateRequirements` guards the opposite order: a spec removal requires
  that no branch changed since, "so that old specs won't be written",
  though on 1.12.0 not main (C21 adds it).
  Closing this order on REST needs a requirement on the writer's side,
  say that the specs its manifests use still exist, or a check in the
  server's commit. That is a REST spec change, so it belongs in its own
  discussion.
- **Where to check.** `specForNewFiles` covers the writes that would hit
  the `NullPointerException`; the manifest check covers the rest. A
  reviewer may prefer one check before `apply(base, parent)` of the specs
  of everything the producer adds. That would need each producer to list
  them.
- **Exception.** `ValidationException` matches the conflict checks a
  commit runs on its refreshed base, and is not retried. A retry could
  not succeed: the spec cannot be re-added under its old id.
- **Schemas.** The same expiry removes unused schemas. A commit writes
  the current schema's id into its snapshot, and the expiry keeps the
  current schema, so no commit applied on the client can name a removed
  one. One applied on newer metadata, as a REST server applies it, can:
  its snapshot names the schema that was current where it was built.
  fileio-catalog's catalog transactions commit that way, and had both
  this and the spec case (its Bug 69, fixed by checking each added
  snapshot's schema and specs).

## In fileio-catalog

There was no workaround: the fuzzer counts any exception but the
expected rejections as unexpected without an injected fault. With the
fix, the append's `ValidationException` is a rejection, and the fuzzer
checks that the catalog did not change. The canary is
`TestIcebergCoreIssues.anAppendNeverCommitsFilesOfARemovedSpec`. It
asserts only that the append does not fail with a `NullPointerException`
and that every manifest of the table names a spec the table has. A fix
that keeps the spec passes too.
