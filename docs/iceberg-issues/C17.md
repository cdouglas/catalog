## Summary

Three metadata updates fail with `CommitFailedException` when another
writer commits while they run, where other updates retry and succeed:

- `UpdateLocation`, for a table and for a view, refreshes once before
  its retry loop and commits on that metadata on every attempt. One
  concurrent commit fails every retry.
- `UpdatePartitionStatistics` commits once, on the handle's metadata,
  with no refresh and no retry. A handle that is not current fails.

## Reproduction

```java
// table operations that run another writer's commit just before their first commit
Table racing = new BaseTable(racingOps(() ->
    catalog.loadTable(ID).updateProperties().set("k", "v").commit()), "t");

racing.updateLocation().setLocation(newLocation).commit();
// CommitFailedException, after all retries

UpdatePartitionStatistics update = table.updatePartitionStatistics().setPartitionStatistics(file);
catalog.loadTable(ID).newFastAppend().appendFile(FILE_B).commit();   // another writer
update.commit();
// CommitFailedException
```

## Cause

- `SetLocation.commit()` refreshes before the loop and commits on that
  `base` in each attempt
  ([SetLocation.java#L55-L64](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/SetLocation.java#L55-L64)).
- `SetViewLocation.commit()` does the same
  ([view/SetViewLocation.java#L52-L68](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/view/SetViewLocation.java#L52-L68)).
- `SetPartitionStatistics.commit()` commits once on `ops.current()`
  ([SetPartitionStatistics.java#L58-L62](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/SetPartitionStatistics.java#L58-L62)).

`SetStatistics` refreshes in each attempt since #15148
([SetStatistics.java#L76](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/SetStatistics.java#L76)).

## Impact

Nothing is lost: the update fails and the table is unchanged. But the
caller must retry the whole operation itself. For partition statistics,
#18204 describes the cost: `compute_partition_stats` writes the
statistics file and then fails to register it, leaving an orphan file.

## Fix

Each attempt refreshes and commits on what it read, as `SetStatistics`
does, and `SetPartitionStatistics` retries like the other updates:

```java
.run(
    taskOps -> {
      // each attempt commits on the table as it is then: a retry follows another commit
      TableMetadata base = taskOps.refresh();
      taskOps.commit(base, base.updateLocation(newLocation));
    });
```

The retry settings are read from `ops.current()`, as `SetStatistics`
reads them.

## Tests

- `TestSetLocation` (new), on every format version: a plain location
  change, and `setLocationRetryWithConcurrentModification`.
- `TestSetPartitionStatistics.setPartitionStatisticsRetryWithConcurrentModification`
  and `setPartitionStatisticsRetrySuccess`, modelled on #15148's tests
  of `SetStatistics`.
- `TestInMemoryViewCatalog.updateViewLocationRetryWithConcurrentModification`.

The 13 new cases other than the plain location change fail without the
fix.
With it, those classes, `TestSetStatistics`, `TestTransaction` and the
full `iceberg-core` test task pass.

## Before a PR

- **Coordinate with #18204**, which covers the partition statistics
  part with the same change. If it merges first, this becomes a
  location-only change.
- **Correct #18204's description.** It says "`SetLocation`-style
  updates" already retry in this situation; the location part of this
  issue shows they don't.
- **Is it a bug?** On #14735, wypoon argued it isn't: "this is not a bug.
  The `compute_table_stats` failed because the snapshot that the stats
  were computed for is no longer the current snapshot". #15148 settled
  that for table statistics, and its reviewers asked for this pattern
  (huaxingao, member: "local base/updated variables per retry attempt").
- **One PR or two.** Tables and views share the bug and the fix; a
  reviewer may still want the view change on its own.

## In fileio-catalog

No workaround. `TableScript` updates locations and partition statistics,
but its stale handles run in the differential property, where both
catalogs fail alike. The canary is
`TestIcebergCoreIssues.aLocationUpdateRetriesOnARefreshedTable`. It
asserts only that a location update after one concurrent commit
succeeds.
