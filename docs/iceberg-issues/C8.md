# C8. A deletion vector older than its data file leaves a table Iceberg can't plan

| | |
|---|---|
| **Affects** | Iceberg 1.12.0, and `main` at `524fe9e` (2026-10-16; the files involved are unchanged at `9bbee07`, 2026-10-18). |
| **Upstream** | Not reported (searched apache/iceberg issues and PRs for the message, 2026-10-18). |
| **Fix** | [`1d46241`](https://github.com/cdouglas/iceberg/commit/1d46241c7cb1693801b1f6b2dc5300e233e5495e) on [`core-fixes`](https://github.com/cdouglas/iceberg/tree/core-fixes), "Core: Skip a DV older than its data file, and refuse to add a data file a DV names". 7 files, +123. Cherry-picks onto `main` at `9bbee07` after C6 (its `TestWapWorkflow` test sits next to C6's). |
| **Found by** | fileio-catalog's `TestInlineDifferentialProperties`, at try 999 of a 6,000-try run (seed 1752781512292409589): planning `main` failed in both catalogs alike. |

## Summary

A row delta adds a deletion vector (DV) for a data file named by path. It
does not check that the file is live where it commits unless the caller
names the file in `validateDataFilesExist`. So it can commit a DV for a file that is
not live on the branch: through a stale handle that still sees the file,
or for a file that is only staged.

Nothing then stops a later commit from adding that file. A cherry-pick
of the snapshot that has it gives the file a newer data sequence number
than its DV. From then on, planning the branch fails:

```
DV data sequence number (5) must be greater than or equal to data file sequence number (6)
```

The symptom is [C6](C6.md)'s, but the path is different: here the
cherry-pick is a file's first pick, so C6's fix, which refuses picking
data files already live, does not apply.

## Reproduction

```java
Table table =
    catalog.buildTable(ID, SCHEMA).withProperty(TableProperties.FORMAT_VERSION, "3").create();
table.newFastAppend().appendFile(file("x")).commit();
DataFile staged = file("d");
table.newFastAppend().appendFile(staged).stageOnly().commit();
long stagedId = Iterables.getLast(table.snapshots()).snapshotId();
table.newRowDelta().addDeletes(dv(table, staged)).commit();  // d is not live on main
table.manageSnapshots().cherrypick(stagedId).commit();       // adds d, newer than its DV

table.newScan().planFiles();  // ValidationException: DV data sequence number ...
```

The fuzzer reached it with a stale handle instead of a staged file:

1. A table's first append adds `f0`; a staged append and two replace
   transactions leave that snapshot off main's history.
2. A position delete through a handle loaded before the replaces plans
   `f0` as live and commits a DV for it on the replaced main, where `f0`
   is not live.
3. A cherry-pick of the first snapshot adds `f0` again, at sequence
   number 6; its DV has 5.

## Cause

`DeleteFileIndex.findDV`
([DeleteFileIndex.java#L217](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/DeleteFileIndex.java#L217))
looks up a data file's DV by path and throws if the DV's data sequence
number is below the file's. The v3 spec says when a DV must apply: when
the data file's data sequence number is at most the DV's, and the path
and partition match. It does not make the other case an error, and no
commit prevents it:

- `RowDelta` adds a DV for any path unless the caller names the file in
  `validateDataFilesExist` (Iceberg's engines do; the API does not
  require it);
- a commit that adds a data file does not check for a DV of its path.

## Impact

- **Unplannable branch:** every scan of the branch fails until the DV or
  the file is removed, which itself needs a commit that plans.
- **Who can hit it:** a client that commits row deltas without
  `validateDataFilesExist`, and a workflow that later adds the file
  again, such as a cherry-pick or write-audit-publish of a snapshot from
  before a replace.

## Fix

Two parts, each enough for a table built only by fixed writers; together
they also cover tables already in this state:

1. **Planning** (`DeleteFileIndex.findDV`): a DV whose data sequence
   number is below its data file's does not apply to it, as the spec's
   rule implies, and is skipped with a warning instead of failing the
   plan. A table that already has such a DV plans again, and reads the
   re-added file whole.
2. **Commits that add data files** (`SnapshotProducer.validateNoDVsForAddedDataFiles`,
   called by `FastAppend.validate` and `MergingSnapshotProducer.apply`, so
   by every operation that adds a data file: append, cherry-pick,
   overwrite, replace partitions, row delta, rewrite): a commit that adds a
   data file whose path a live DV in its parent names is refused. It reads
   only the parent's delete manifests that can hold an added file's
   partition, and only on v3 and later.

Iceberg tolerates dangling DVs (it removes them when it deletes their
files, and maintenance removes others), so the fix does not refuse the row
delta that commits one: that check failed 44 of the delete-related core
tests, which commit DVs for files they never add, and read every data
manifest on each DV commit. A dangling DV is harmless until its path is
added again, which is what the second part refuses.

## Tests

- `DeleteFileIndexTestBase.testDVOlderThanItsDataFileDoesNotApply`
  (replacing `testInvalidDVSequenceNumber`, which asserted the exception):
  the DV applies to a data file of its own sequence number and not to a
  newer one.
- `TestWapWorkflow.testCherrypickOfAFileADVNames`: the reproduction
  above; the pick is refused and the table keeps its files.
- `TestFastAppend.testAppendOfAFileADVNames`: a fast append and a merge
  append of a file a dangling DV names are refused; another file appends.

Each fails on `core-fixes` without the fix (v3 and v4). With it, the full
`iceberg-core` check passes.

## Before a PR

- **It changes a deliberate assertion.** Upstream's
  `testInvalidDVSequenceNumber` asserts that planning fails on a DV older
  than its data file. The PR has to argue that the spec makes such a DV
  inapplicable rather than invalid, and that failing every plan of the
  branch is worse than a warning.
- **Cost:** the commit check reads delete manifests on appends to v3
  tables that have DVs, pruned by the added files' partitions. A cheaper
  variant could skip it when the parent has no DVs at all, from the
  snapshot summary (`total-delete-files`).
- **Alternative:** remove the dangling DV in the commit that re-adds the
  file instead of refusing the commit, as Iceberg removes the DVs of the
  data files a commit deletes.

## In fileio-catalog

The workaround was in `TestInlineDifferentialProperties.files`: a planning
failure with this message compared as the string "fails (C8): ...", which
both catalogs had to produce alike; it is gone with the fix. The canary
`TestIcebergCoreIssues.aDataFileADeletionVectorNamesIsNotAddedAgain`
asserts the bug is absent: the cherry-pick is refused and the table plans.
