## Summary

`ExpireSnapshots` reads four table settings when it is created, from the
metadata its table handle has then:

- `gc.enabled`, which it checks;
- `history.expire.max-snapshot-age-ms`, `history.expire.min-snapshots-to-keep`
  and `history.expire.max-ref-age-ms`, its defaults for what to retain.

Each commit attempt refreshes the metadata it commits on, and follows the
retention of that metadata's refs, but keeps the table settings from
creation. If another writer changes them in between, the expiry ignores
the change:

- an expiry created before another writer disabled GC, as for a table
  that shares files with another, deletes files anyway;
- one created before another writer raised the table's retention expires
  snapshots the new retention keeps;
- one created before another writer gave refs a maximum age keeps refs
  that have passed it.

A branch's own retention (`ManageSnapshots.setMinSnapshotsToKeep` and
the like) set in between is followed, so the two ways to set the same
retention behave differently.

## Reproduction

```java
Table table = catalog.loadTable(ID);   // three snapshots, the newest ones
ExpireSnapshots expire = table.expireSnapshots().expireOlderThan(System.currentTimeMillis());

Table other = catalog.loadTable(ID);   // another writer
other.updateProperties().set(TableProperties.MIN_SNAPSHOTS_TO_KEEP, "3").commit();

expire.commit();
Iterables.size(catalog.loadTable(ID).snapshots());   // 1, not 3
```

With `other.manageSnapshots().setMinSnapshotsToKeep("main", 3)` in
place of the property, the expiry keeps 3. With
`set(TableProperties.GC_ENABLED, "false")`, the expiry commits and
deletes the expired snapshots' files.

## Cause

The constructor checks `gc.enabled` and computes `defaultExpireOlderThan`,
`defaultMinNumSnapshots` and `defaultMaxRefAgeMs` from `ops.current()`
([RemoveSnapshots.java#L84-L103](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/RemoveSnapshots.java#L84-L103)).
`internalApply` refreshes `base` on each attempt
([#L196-L197](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/RemoveSnapshots.java#L196-L197))
and reads each ref's retention from it, falling back to those defaults
([#L289](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/RemoveSnapshots.java#L289),
[#L310](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/RemoveSnapshots.java#L310)).
Nothing checks `gc.enabled` again.

## Impact

- **GC.** `gc.enabled=false` protects tables that share data files, for
  example after a snapshot or migrate procedure: deleting a file another
  table references corrupts that table. An `expire_snapshots` job started
  before GC was disabled deletes files after it was disabled. The window
  is from the expiry's creation to its commit, which for a job that plans
  first can be long.
- **Retention.** Raising `history.expire.min-snapshots-to-keep` or
  `max-snapshot-age-ms`, say to keep history for an investigation, does
  not stop an expiry already under way from removing that history. The
  snapshots are gone for good.
- **Ref age.** An expiry keeps refs past a maximum age set while it ran.
  That is only late: the next expiry removes them.

## Fix

`internalApply` checks `gc.enabled` and reads the three defaults on the
metadata it has just refreshed, keeping what the caller set with
`expireOlderThan` and `retainLast`:

```java
this.base = ops.refresh();
// the table's GC and retention settings, from the metadata this attempt commits on: another
// writer may have changed them since this expiry was created
checkGcEnabled(base);
this.defaultExpireOlderThan =
    expireOlderThan != null
        ? expireOlderThan
        : now - PropertyUtil.propertyAsLong(base.properties(), MAX_SNAPSHOT_AGE_MS, ...);
this.defaultMinNumSnapshots =
    minNumSnapshots != null
        ? minNumSnapshots
        : PropertyUtil.propertyAsInt(base.properties(), MIN_SNAPSHOTS_TO_KEEP, ...);
this.defaultMaxRefAgeMs =
    PropertyUtil.propertyAsLong(base.properties(), MAX_REF_AGE_MS, MAX_REF_AGE_MS_DEFAULT);
```

The check on creation stays, so an expiry of a table with GC disabled
still fails at once. `now` is still taken on creation: ages are measured
from when the caller asked.

## Tests

In `TestRemoveSnapshots`, on every format version, with incremental
cleanup and without:

- `testRetentionRaisedSinceCreated`: the reproduction. The expiry keeps
  3 snapshots.
- `testRefAgeSetSinceCreated`: another writer sets
  `history.expire.max-ref-age-ms` to 1 ms after the expiry is created; the
  expiry removes the tag that has passed it.
- `testGcDisabledSinceCreated`: another writer disables GC after the
  expiry is created; the commit fails with `ValidationException`
  ("Cannot expire snapshots: GC is disabled"), deletes nothing, and the
  table keeps its snapshots.

All 24 cases fail on 1.12.0. With the fix, `TestRemoveSnapshots` (560
cases) and the full `iceberg-core` test task pass.

## Before a PR

- **Is it a bug?** One could argue an expiry is configured when it is
  created. But it already reads each ref's retention per attempt, and
  `gc.enabled` is a safety switch: an operation that commits after it is
  set should not delete files. A serial order of the two commits never
  gives the current outcome.
- **Coordinate with #17791.** The two conflict in `RemoveSnapshots`. Its
  per-attempt check is this fix's; it also changes what `gc.enabled`
  gates, which is being settled on dev@ ("[DISCUSS] Defining gc.enabled
  semantics across engines and clients", 2026-09-11). Offer the retention
  part on its own, or on top of #17791.
- **`now`.** The fix keeps `now` from creation. Taking it per attempt
  would expire a little more on a retry; either is defensible, and
  keeping it is the smaller change.
- **Other operations.** Other operations that delete files on commit,
  such as `RewriteManifests` and a table purge, could be checked for the
  same pattern; not done here.

## In fileio-catalog

The fuzzer's model does not follow snapshot history, so it could not
see the retention cases; its model of refs treats a ref that may age out
as possibly gone, so it could not see the ref case either. Nothing in
fileio-catalog worked around it. The canary is
`TestIcebergCoreIssues.anExpiryFollowsSettingsChangedSinceItWasCreated`.
It asserts only that an expiry created before GC was disabled deletes
nothing, and that one created before retention was raised keeps what the
new retention keeps.
