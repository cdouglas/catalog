# C16. A rollback undoes another writer's rollback, or fails with an NPE when its target expires

| | |
|---|---|
| **Affects** | Iceberg 1.12.0, and `main` at `834441b96` (2026-10-21), on every catalog. |
| **Upstream** | Not reported (searched apache/iceberg issues and PRs, 2026-10-20). |
| **Fix** | [`14d869e`](https://github.com/cdouglas/iceberg/commit/14d869e9d4d0c135c736f775d26dbea9ce49f735) on [`core-fixes`](https://github.com/cdouglas/iceberg/tree/core-fixes), "Core: Check a rollback's target on each attempt". 2 files, +66 -1. Cherry-picks cleanly onto `main` at `834441b96`. |
| **Found by** | fileio-catalog's review of Iceberg's commit retry paths for state read before an attempt, 2026-10-20. Reproduced in `TestSnapshotManager`. |

## Summary

`ManageSnapshots.rollbackTo(id)` checks that the snapshot is an ancestor
of main's head when it is called. The commit refreshes the table and
does not check again. Two races follow:

- Another writer rolls main back further, past the target. The rollback
  then moves main forward again, to a snapshot no longer in its history,
  which undoes the other writer's rollback. Run in either order, the two
  rollbacks end with main at the older snapshot, or the later one fails.
- Another writer expires the target. `rollbackTo` and
  `setCurrentSnapshot` then fail with a `NullPointerException`.

## Reproduction

```java
table.newFastAppend().appendFile(FILE_A).commit();      // s1
table.newFastAppend().appendFile(FILE_B).commit();      // s2
table.newFastAppend().appendFile(FILE_C).commit();      // s3
ManageSnapshots rollback = table.manageSnapshots().rollbackTo(s2);

catalog.loadTable(ID).manageSnapshots().rollbackTo(s1).commit();   // another writer

rollback.commit();
table.refresh();
table.currentSnapshot().snapshotId();                   // s2: main moved forward again
```

With `expireSnapshotId(s1)` by the other writer instead, after
`rollbackTo(s1)` or `setCurrentSnapshot(s1)`, the commit fails with
`NullPointerException: Cannot invoke "Snapshot.snapshotId()" because
"snapshot" is null`.

## Cause

`SetSnapshotOperation.rollbackTo` checks the target's ancestry on the
metadata the operation was created with
([SetSnapshotOperation.java#L78-L89](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/SetSnapshotOperation.java#L78-L89)).
`apply()` refreshes, and checks ancestry again only if `isRollback` is
set ([#L93-L106](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/SetSnapshotOperation.java#L93-L106)),
which only `rollbackToTime` sets
([#L73](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/SetSnapshotOperation.java#L73)).
It returns `base.snapshot(target)`, null once the snapshot has been
expired, and `commit()` dereferences it
([#L123](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/SetSnapshotOperation.java#L123)).

## Impact

Two operators rolling a table back after a bad write, one further than
the other, can end with the table at the newer of the two targets, with
the bad data that the further rollback removed. Each sees its rollback
succeed. The expiry race only gives an unhelpful exception; the table
is unchanged.

## Fix

`apply()` checks, on the metadata it has just refreshed, that the table
still has the target, and `rollbackTo` sets `isRollback`, so that its
target must still be an ancestor of main:

```java
// another writer may have expired the snapshot since it was set
ValidationException.check(
    base.snapshot(targetSnapshotId) != null,
    "Cannot roll back to %s: the table no longer has it",
    targetSnapshotId);
```

Both failures are `ValidationException`s, as when the call itself
follows the other writer's change.

## Tests

In `TestSnapshotManager`, on every format version:

- `testRollbackToAfterConcurrentRollbackPastIt`: the reproduction. The
  commit fails, and main stays at s1.
- `testRollbackToSnapshotExpiredConcurrently` and
  `testSetCurrentSnapshotExpiredConcurrently`: the expiry race, for both
  calls.

All 12 cases fail without the fix. With it, `TestSnapshotManager`,
`TestWapWorkflow`, `TestSequenceNumberForV2Table`,
`TestIncrementalDataTableScan`, `TestTransaction` and the full
`iceberg-core` test task pass.

## Before a PR

- **`setCurrentSnapshot`** may set main to any snapshot, so the fix
  checks only that it still exists. That is the documented difference
  between the two calls.
- **Message.** The call-time check says "Cannot roll back to unknown
  snapshot id"; the new one says the table no longer has it. Reviewers
  may prefer one wording, as for C14.
- **`rollbackToTime`** picks its target when it is called. After a
  concurrent rollback of main past that target, it now fails, as it did
  before; a serial run might have picked another target. Not changed.

## In fileio-catalog

No workaround. `TableScript` rolls back, but only through handles that
see the table as it is, or in the differential property, where both
catalogs act the same. The canary is
`TestIcebergCoreIssues.aRollbackDoesNotUndoAConcurrentRollbackPastIt`.
It asserts only that main stays where the other writer's rollback put
it.
