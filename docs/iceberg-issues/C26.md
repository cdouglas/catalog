## Summary

The spec allows at most one deletion vector (DV) per data file in a
snapshot. A row delta that adds a DV for a data file therefore checks,
in v3 and whatever its other validations, that no commit since its
starting snapshot added a DV for the same file
(`MergingSnapshotProducer.validateAddedDVs`). The check read only the
delete manifests, and the entries in them, that the operation's conflict
detection filter matches.

That filter is the caller's statement of the rows the operation read: it
scopes the isolation checks the caller asks for (no conflicting data
files, no conflicting delete files). Nothing requires it to cover every
data file the operation adds a DV for. When it doesn't, a DV that another
writer added for such a file since the operation began is never seen, and
the commit adds a second one. Unlike the isolation checks, this one
protects the table itself: with two DVs for one file, no scan of the
table can be planned.

## Reproduction

```java
// v3, partitioned by identity(id); data file F in partition id=2
long start = table.currentSnapshot().snapshotId();
RowDelta delta = table.newRowDelta()
    .addDeletes(dvFor(F))
    .validateFromSnapshot(start)
    .conflictDetectionFilter(Expressions.equal("id", 1))  // misses F's partition
    .validateNoConflictingDeleteFiles();

otherWriter.newRowDelta().addDeletes(anotherDvFor(F)).commit();
delta.commit();                                        // commits

table.refresh();
table.newScan().planFiles();  // ValidationException: Can't index multiple DVs for F
```

`TestIcebergCoreIssues.aConcurrentDvOutsideTheConflictFilterIsCaught`
runs this on `InMemoryCatalog`; it fails on 1.12.0 and on `main` at
`97659351d4`.

## Cause

`validateAddedDVs`
([MergingSnapshotProducer.java#L869-L899](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/MergingSnapshotProducer.java#L869-L899))
keeps the new delete manifests that `filterManifestsByPartition` matches
to the filter's inclusive projection
([#L891](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/MergingSnapshotProducer.java#L891)),
and reads their entries with `filterRows(conflictDetectionFilter)`
([#L905](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/MergingSnapshotProducer.java#L905)).
A DV of a file outside the filter is dropped at either step.
`DeleteFileIndex` then refuses the table
([DeleteFileIndex.java#L573](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/DeleteFileIndex.java#L573)).

## Impact

Every scan of the table from the bad snapshot on fails during planning:
reads, row-level operations and maintenance alike. Recovery is a rollback
to the snapshot before it, which also drops every commit since, or a
repair by hand; maintainers want it so (#17206). Spark derives the filter
from the filters of the scan whose rows it rewrites, so its DVs usually
fall inside it; a caller whose filter is narrower than the files it adds
DVs for hits it, as the fuzzer did.

## Fix

A DV is in the partition of the data file it references, so a
concurrent DV for a file the commit adds one for is in a partition of the
commit's own DVs. Scope the check by those partitions instead of by the
filter. This keeps #15653's pruning, which #15966 gave up, without
depending on the filter:

```java
PartitionSet partitions = PartitionSet.create(base.specsById());
for (List<DeleteFile> dvs : dvsByReferencedFile.values()) {
  for (DeleteFile dv : dvs) {
    partitions.add(dv.specId(), dv.partition());
  }
}

Iterable<ManifestFile> matchingManifests =
    Iterables.filter(
        newDeleteManifests,
        manifest ->
            manifest.hasAddedFiles()
                && ManifestFileUtil.canContainAny(manifest, partitions, base.specsById()));
```

The entries are read unfiltered. `validateAddedDVs` no longer takes the
filter, and `filterManifestsByPartition`, which only it used, is gone.

## Tests

- `TestRowDelta.testConcurrentDVOutsideTheConflictDetectionFilter`, on
  v3 and v4, on `main` and on a branch: #15966's case, DVs for files in
  two partitions, a filter that covers one, and a concurrent DV for the
  other's file. All four cases fail without the fix (the commit
  succeeds).
- #15653's tests (`testConcurrentDVsInDifferentPartitionsWithFilter`,
  `testConcurrentDVsInSamePartitionWithFilter`,
  `testDVValidationPartitionPruningManifestCount`) pass with it: their
  concurrent DVs are in other partitions, which the commit's DVs do not
  cover either.

With the fix, `TestRowDelta` and the full `iceberg-core` test task pass.

  amogh-jahagirdar, who reviewed it.
- **Cite #17206** as the consequence: maintainers want a table with two
  DVs for a file to fail hard, so the write side must never produce one.
- **Check with #17754 and #18224**, which touch the same check.

## In fileio-catalog

No workaround: Bug 77 was the fuzzer's own (its scans now include column
stats). The canary,
`TestIcebergCoreIssues.aConcurrentDvOutsideTheConflictFilterIsCaught`,
asserts only that the table stays plannable after the race, so a fix that
merges the two DVs passes too. The fork's commit footprint for a row
delta records this check's scope, now the partitions of its DVs, which
the conflict encodings partition-vector and manifest-window read.
