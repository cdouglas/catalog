# C36. A transaction retried after a conflict lists an earlier update's manifest with its first attempt's sequence numbers

| | |
|---|---|
| **Affects** | Iceberg 1.12.0, and `main` at `e70a2efcd0` (2026-10-21): `ManifestFilterManager.filterManifest`'s cache, under a transaction (`BaseTransaction`) whose commit retries, when a later update of the transaction (a `replacePartitions`, an overwrite, a delete) keeps unchanged a manifest an earlier update of it wrote. Format v2; on v3 and later the fork's C2 fix already filters again, since the retry gives the manifest another first row id. |
| **Upstream** | Not reported (searched apache/iceberg's issues, PRs and PR branches, and the issues@ and dev@ lists, 2026-11-20). Open PR [#18074](https://github.com/apache/iceberg/pull/18074) ("Core: Skip manifest list re-reads after successful commits") keys a related cache by location for transaction retries, and does not touch this one. |
| **Fix** | `core-fixes` [`1c38c22`](https://github.com/cdouglas/iceberg/commit/1c38c22dc6), "Core: Filter a retried transaction's manifests again when their sequence numbers changed". |
| **Found by** | fileio-catalog's rebase oracle, round p26-r0 (2026-11-20): R a table transaction (an append, then a partition replace) raced by a replace and a rewrite; its retried record named the append's manifest at sequence number 4 in the append's snapshot and 2 in the replace's, and the catalog's replay check refused the restated pooled manifest (`ReplayCheckError`). |

## Summary

`ManifestFilterManager` caches each manifest it filtered, keyed by the input
manifest, which `GenericManifestFile` compares by path, so that a commit that
retries need not read or rewrite it again. A manifest that has no file to
remove is cached as itself.

A transaction's retry (`BaseTransaction.applyUpdates`) applies each of its
updates again on the table as it is. Each of its snapshots gets a sequence
number above the other writers' commits, so an append's new manifest comes
back under the same path with higher sequence numbers. A later update of the
transaction that keeps that manifest unchanged asks the cache for it, finds
the first attempt's copy, with the first attempt's sequence numbers, and
writes it into its manifest list. The two snapshots of the retried
transaction then disagree on the manifest's sequence number.

On a v2 table, the appended files carry no sequence number of their own
(`ADDED` entries inherit the manifest's), so through the later snapshot they
read with a data sequence number below their snapshot's: an equality delete
another writer committed between the two attempts, which should not apply to
rows the transaction added after it, applies to them.

On v3 and later, the fork's C2 fix compares the cached manifest's first row
id with the input's, and the retry gives the manifest a new one, so the cache
is not used.

## Reproduction

On `InMemoryCatalog`, format 2, partitioned:

1. a table with one data file;
2. a transaction appends a second file, then replaces a third file's
   partition (keeping the append's manifest);
3. another writer appends a file and commits an equality delete in the
   second file's partition;
4. the transaction commits (it retries once).

The replace's snapshot lists the append's manifest at the first attempt's
sequence number, below the append's snapshot's, and a scan of the table reads
the second file with the other writer's equality delete. With the transaction
committed before the other writer, or alone, neither happens.

## Cause

`ManifestFilterManager.filterManifest` (1.12.0):

```java
ManifestFile cached = filteredManifests.get(manifest);
if (cached != null) {
  return cached;   // the first attempt's copy, whatever the input's numbers now
}
```

The cache's key is equal by path alone, and a retried transaction's earlier
update writes the same path with other sequence numbers.

## Fix

Keep, with each cached manifest, what a commit assigns the input (its first
row id, sequence number and minimum sequence number), and filter it again
when they changed. The fork's C2 fix already kept the first row id; this
widens it to the sequence numbers.

`ManifestMergeManager`'s cache has the same rule (its C2 check compares first
row ids only). A test whose retry merges the same bin, with the other writer
committing to another branch, passed before the fix, so no change was made
there.

## Tests

`TestTransaction.testTransactionRetryKeepsTheSequenceNumbersOfItsEarlierCommits`
(the replace's manifest list names the append's manifest at the append's
sequence number) and
`testTransactionRetryKeepsItsRowsFromDeletesCommittedBetweenItsAttempts` (a
scan reads the appended file without the other writer's equality delete), for
format versions 2 to 4: both fail on v2 before the fix and pass after.
`TestTransaction` (112), `TestReplacePartitions` (240), `TestOverwrite` (112),
`TestDeleteFiles` (121), `TestRowDelta` (372) and `TestRowLineageMetadata`
(21) pass.

## Before a PR

Upstream has no C2 check, so the fix there is the cache's comparison itself,
with the same tests; on v3 upstream presumably shows it too (C2's own issue
then also applies).

## In fileio-catalog

Canary `TestIcebergCoreIssues.aRetriedTransactionKeepsTheSequenceNumbersOfItsManifests`
(a delete of another file keeps the append's manifest). The catalog's replay
refuses a record that restates a pooled manifest with another entry (`pool:
restates a pooled manifest`), and its replay check (`ReplayCheckError`) caught
a merged one before the rule's rejection did: the subject merged the retried
transaction's record, whose two snapshots named the manifest differently.
