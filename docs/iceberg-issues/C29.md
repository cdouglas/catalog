# C29. A load racing a drop with purge reports a missing metadata file

| | |
|---|---|
| **Affects** | Iceberg 1.12.0, and `main` at `e70a2efcd0` (2026-10-21): every catalog whose table operations extend `BaseMetastoreTableOperations` (JDBC, Hive, Glue, DynamoDB, Nessie, and others), and views through `BaseViewOperations`. Nothing found on a load whose file is deleted after the load read the catalog. ## Summary

A metastore's `doRefresh` reads the table's metadata location from the
catalog, and `refreshFromMetadataLocation` then reads the file there. A
drop with purge deletes the table's files once its catalog change lands,
and a commit with `write.metadata.delete-after-commit.enabled` deletes the
metadata files that fall out of the metadata log. Either can land between
a load's two reads and delete the file the load is about to read. The read
fails with `NotFoundException`, which `refreshFromMetadataLocation` does
not retry, and `refresh` passes it on. The catalog no longer names the
file: the table was dropped, or it moved on and is there.

## Reproduction

`TestJdbcCatalog` and `TestJdbcViewCatalog` on the fork interleave the
race through the catalog's FileIO (a `HadoopFileIO` that runs another
operation just before it opens the next metadata file):

| Case | 1.12.0 | Fixed |
|---|---|---|
| `loadTable` reads the location; the table is dropped with purge; the load reads the file | NotFoundException | NoSuchTableException |
| A handle's refresh reads the new location after a commit; the table is dropped with purge | NotFoundException | NoSuchTableException |
| A load reads the location; two commits land, the second deleting that file (`previous-versions-max` 1) | NotFoundException | loads the newest version |
| `loadView` reads the location; the view is dropped (`gc.enabled`) | NotFoundException | NoSuchViewException |
| The file the catalog names is gone (`CatalogTests.testLoadTableWithMissingMetadataFile`) | NotFoundException | NotFoundException |

## Cause

`BaseMetastoreTableOperations.refresh` calls `doRefresh` once.
`doRefresh` reads the location and calls `refreshFromMetadataLocation`,
whose retries stop on `NotFoundException`: a missing file is taken for a
lost one, which retrying would not bring back. That holds only while the
catalog still names the file, and nothing checks that it does.
`BaseViewOperations.refresh` is the same.

## Impact

- A load or refresh racing a drop with purge fails with
  `NotFoundException`, not the `NoSuchTableException` the `Catalog` and
  `Table` contracts name for a missing table. A caller that handles a
  missing table gets an error instead: `Catalog.tableExists`' default
  (JDBC's; Hive overrides it) loads the table, catches only
  `NoSuchTableException`, and throws.
- With `write.metadata.delete-after-commit.enabled` and a small
  `previous-versions-max`, a load racing commits fails though the table
  is there. A writer's refresh before its commit fails the same way, and
  the operation fails, not retries.
- Nothing is lost: the error is the wrong one, and the failed operation
  committed nothing.

## Fix

`BaseMetastoreTableOperations.refresh` calls `doRefresh` again when it
throws `NotFoundException`. The second read of the catalog finds the table
dropped (`doRefresh` throws `NoSuchTableException`, or, for operations
that never loaded the table, leaves no metadata, so `loadTable` throws
it), or names the file that holds the table now and loads it. A file the
catalog still names is lost, and the second read throws
`NotFoundException` as before, so
`CatalogTests.testLoadTableWithMissingMetadataFile` still holds.
`BaseViewOperations.refresh` does the same. One retry: a second race in
the same refresh fails as before.

## Tests

`TestJdbcCatalog`: `testLoadRacingADropWithPurgeFindsTheTableDropped`,
`testRefreshRacingADropWithPurgeFindsTheTableDropped`,
`testLoadRacingCommitsThatDeleteItsMetadataFileFindsTheNewOne`;
`TestJdbcViewCatalog`: `testLoadRacingADropFindsTheViewDropped`. Each
fails on `core-fixes` without the fix with `NotFoundException`; the JDBC
suites (223 tests) pass with it, `testLoadTableWithMissingMetadataFile`
among them.

## Before a PR

Frame it by upstream's own reading of `NotFoundException`: a lost file is
one the catalog still names (`testLoadTableWithMissingMetadataFile`,
#12511), and a drop already tolerates a lost file (#5510). The retry is in
the shared `refresh`, so every metastore gets it; run the Hive and Glue
suites. C27's fix sits beside it in both `refresh` methods: on `main`,
which lacks C27, the change applies by hand.

## In fileio-catalog

No workaround to remove. `LogCatalog`'s table operations read the catalog
again themselves when a pointer table's file is missing (Bug 86 (load
racing a purge), `FileIOTableOperations.readPastMissing`), and an
operation that loads a table from the read it stages on (a drop with
purge, a reinline, a catalog transaction's commit) takes the file gone as
a change since its read (Bug 87 (staged read racing a purge),
`LogCatalog.tableOpsAsRead`): neither depends on this fix, so both work
on stock Iceberg. The canary
`TestIcebergCoreIssues.aRefreshRacingADropWithPurgeFindsTheTableDropped`
runs C27's canary's metastore operations over an `InMemoryFileIO` that
drops the table between a handle's two reads. catalog-bench's JDBC
baseline runs `core-perf`, which has the fix; its workloads drop no tables
while others load them.
