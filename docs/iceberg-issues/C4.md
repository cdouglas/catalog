# C4. A stale handle fails on a manifest in a newer partition spec

| | |
|---|---|
| **Affects** | Iceberg 1.10.1 and 1.12.0, and `main` at `524fe9e` (2026-10-16). The files the fix changes have not changed on `main` between `524fe9e` and `9bbee07` (2026-10-18). |
| **Upstream** | Not reported (searched apache/iceberg issues and PRs, 2026-10-16). |
| **Fix** | [`bfc20da`](https://github.com/cdouglas/iceberg/commit/bfc20da320f4b40715e17571dab16053637f33d4) on [`core-fixes`](https://github.com/cdouglas/iceberg/tree/core-fixes), "Core: Use the partition specs of the metadata a commit applies to". 8 files, +114/−14. Cherry-picks cleanly onto `main` at `9bbee07`. |
| **Found by** | fileio-catalog's `TestCatalogFaultProperties`, a fuzzer of stale handles and concurrent writers. |

## Summary

A table handle loaded before another writer added a partition spec cannot
run some commits once the table has a manifest written in the new spec.
These fail with a `NullPointerException`, before writing anything:

- a delete by path;
- an overwrite by row filter;
- a dynamic partition replace;
- a row delta that removes a delete file;
- a manifest rewrite.

A fast append, a merge append, and a row delta that only adds files all
commit through the same stale handle.

## Reproduction

On Iceberg's own `InMemoryCatalog`, with a one-column schema `id`:

```java
Table stale = catalog.createTable(ID, SCHEMA);
stale.newFastAppend().appendFile(file("z")).commit();

Table other = catalog.loadTable(ID);
other.updateSpec().addField("id").commit();
other.newFastAppend().appendFile(file(other.spec(), "a")).commit(); // a manifest in spec 1

// each of these throws NullPointerException
stale.newDelete().deleteFile(path("a")).commit();
stale.newReplacePartitions().addFile(file("b")).commit();
stale.rewriteManifests().clusterBy(file -> "all").commit();
```

The failing calls look the new spec up in a map that doesn't have it:

- Delete by path: `Cannot invoke "PartitionSpec.partitionToPath(StructLike)" because "spec" is null`, in `ManifestFilterManager.buildSummary`.
- Overwrite by filter: `Cannot invoke "PartitionSpec.schema()" because "this.spec" is null`, in `ManifestEvaluator.forRowFilter`.
- Replace partitions and the row delta: `Cannot invoke "PartitionSpec.partitionType()"`, in `ManifestFileUtil.canContainAny`.
- Rewrite: `Cannot invoke "PartitionSpec.specId()" because "spec" is null`, in `ManifestWriter.<init>`.

## Cause

`SnapshotProducer.commit` refreshes the table on each attempt and applies
the operation to the refreshed metadata. Most of the operation reads
partition specs from that metadata: the merge managers do, through
`ops().current().spec(specId)`
([MergingSnapshotProducer.java#L1282](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/MergingSnapshotProducer.java#L1282)).
Two parts don't. Each copies the specs of the handle's metadata when the
operation is created:

- The filter managers are created with
  `ops().current().specsById()`
  ([MergingSnapshotProducer.java#L1240](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/MergingSnapshotProducer.java#L1240),
  [#L1309](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/MergingSnapshotProducer.java#L1309)).
  `ManifestFilterManager` keeps that map
  ([ManifestFilterManager.java#L73](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/ManifestFilterManager.java#L73)),
  and looks up each manifest's spec in it
  ([#L261](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/ManifestFilterManager.java#L261),
  [#L423](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/ManifestFilterManager.java#L423),
  [#L432](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/ManifestFilterManager.java#L432),
  [#L442](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/ManifestFilterManager.java#L442)).
- `BaseRewriteManifests` copies the specs in its constructor
  ([BaseRewriteManifests.java#L74](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/BaseRewriteManifests.java#L74)).
  It uses them for each rewritten manifest's writer
  ([#L342](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/BaseRewriteManifests.java#L342)),
  and for `addManifest` copies.

A manifest in a spec added after the handle was loaded has no entry in the
copied map.

## Impact

A writer that holds a table handle while another writer evolves the
partition spec gets an unexpected `NullPointerException`, not a commit or
a `CommitFailedException`. Long-running jobs, and engines that cache
`Table` objects, are where this happens. No data is written wrong: the
failure comes before anything is committed.

## Fix

Look the specs up in the metadata the commit attempt applies to:

- `ManifestFilterManager` takes a `Supplier<Map<Integer, PartitionSpec>>`,
  and `MergingSnapshotProducer` passes `() -> ops().current().specsById()`,
  as its merge managers already do. The class is package-private, so no API
  changes.
- `BaseRewriteManifests` drops its `specsById` field. It uses
  `ops().current().spec(id)` for writers and `current.specsById()` for
  `addManifest` copies.
- The filter manager still creates its two `PartitionSet`s from the specs
  at construction. They hold the partitions of files and partitions given
  to the operation, and those are in specs the handle knows.

## Tests

Each test is a `*WithConcurrentSpecChange` case in the upstream class for
its operation. Each loads a handle, adds a partition field and a file in
the new spec through another handle, then commits through the first. Every
format version, and every branch where the class runs on branches, is
covered:

- `TestDeleteFiles.testDeleteByPathWithConcurrentSpecChange`
- `TestOverwrite.testOverwriteByRowFilterWithConcurrentSpecChange`
- `TestReplacePartitions.testReplacePartitionsWithConcurrentSpecChange`
- `TestRowDelta.testRemoveDeletesWithConcurrentSpecChange`
- `TestRewriteManifests.testRewriteManifestsWithConcurrentSpecChange`

That is 34 cases, and all fail on 1.12.0 with the `NullPointerException`s
above. With the fix, the five classes' 923 tests and the full
`iceberg-core` check pass.

## Before a PR

- **A gap that remains:** a stale handle given a `DataFile` in a spec it
  hasn't seen still fails, when the file is added to a `PartitionSet`. A
  stale handle would normally only get files in specs it knows, from its
  own scans. Supporting this would mean making the `PartitionSet`s lazy
  too.
- **Possible review question:** "why not refresh the specs in
  `MergingSnapshotProducer.apply`?" The supplier keeps the lookups the same
  as the merge managers', and needs no extra state per attempt.
- **Pairs with C5:** C5 touches `BaseRewriteManifests.apply` next to this
  change, but the two commits are independent.

## In fileio-catalog

The workarounds were `staleSpecs`, which turned the exception into a
rejection for merge appends, deletes and row deltas, and the
`rewriteManifests` op's catch, both in `TestCatalogFaultProperties`.
[`63dd25e`](https://github.com/cdouglas/catalog/commit/63dd25e95d4305f079565a38635d4630d574783a)
removed them, with the canary test. With the workarounds removed and
without the fix, the fuzzer finds C4 within 300 tries. A new canary,
`TestIcebergCoreIssues.aStaleHandleCommitsOnAManifestInANewerSpec`,
asserts the bug is absent, for each failing commit in the summary but the
row delta.
