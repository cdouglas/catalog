## Summary

A replace transaction (`buildTable(...).replaceTransaction()` or
`createOrReplaceTransaction()`; REPLACE TABLE, CREATE OR REPLACE TABLE
and RTAS in engines) builds its replacement from the table as it is
when the transaction begins: the new schema, partition spec, sort order
and properties, on top of the table's snapshots, refs and properties.
When it commits, it refreshes the table, and commits that replacement
over whatever the table has become. Everything other writers committed
in between is gone:

- a commit to another branch: the branch goes back, and the commit's
  snapshot is gone from the table, though its writer was told it
  committed;
- a commit to main: its snapshot is gone from history;
- a tag;
- a property, such as `gc.enabled=false` set for a table that shares
  its files, after which an expiry may delete files the other table
  reads;
- a format upgrade, which the replace takes back: the table is
  downgraded, which the spec forbids;
- an expiry: its snapshots come back without their manifest lists
  (C3).

## What upstream considers intended, and what a bug

rdblue, reviewing #16289 (2026-05-15):

> The contract of REPLACE TABLE is that the table's data, schema, and
> partitioning are replaced. There are no assumptions to validate, so
> checking for conflicts between concurrent changes and those changes is
> not required. If this is what you're trying to change, then I'm -1 for
> this commit because it is changing behavior that is already considered
> and chosen.
>
> That said, REPLACE TABLE is also intended to keep table history (it is
> not a drop/re-create). So there are, potentially, valid problems with
> concurrency. For example, if a table's schema is updated from
> schema-id 1 to schema-id 2 and then the REPLACE TABLE operation
> removes the new schema-id 2 -- as though the concurrent commit never
> happened -- then that's a bug that we should fix.

So two parts:

- **Intended:** a replace wins. It replaces the table's data, schema
  and partitioning whatever changed since it began, without a conflict
  check. Two racing replaces end as the second built it:
  `CatalogTests.testConcurrentReplaceTransactions` and its variants
  (from #4319, 2022) assert that.
- **A bug:** the replacement erases what happened in between, as though
  it never happened. Every case in the summary is this one: none is
  part of what a replace replaces.

The fix keeps the first and fixes the second. fileio-catalog's earlier
fix attempt failed a replace on any change, as #16289 did, which is the
intended part; it was dropped for this one.

## Reproduction

```java
table.newFastAppend().appendFile(FILE_A).commit();
table.manageSnapshots().createBranch("b", first).commit();
Transaction replace = catalog.buildTable(ID, SCHEMA).replaceTransaction();
replace.newFastAppend().appendFile(FILE_C).commit();

Table other = catalog.loadTable(ID);
other.newFastAppend().appendFile(FILE_B).toBranch("b").commit();   // s2 on b
other.manageSnapshots().createTag("t", first).commit();
other.updateProperties().set("gc.enabled", "false").commit();

replace.commitTransaction();
// branch b is back at s1, s2 is gone; no tag t; gc.enabled is unset
```

## Cause

`BaseTransaction.commitReplaceTransaction` refreshes the table and
commits the transaction's `current`, the replacement as it was built
and updated, over it
([BaseTransaction.java#L297-L348](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/BaseTransaction.java#L297-L348)):
"because this is a replace table, it will always completely replace the
table metadata. even if it was just updated." The transaction has no
way to build the replacement again: the catalog's table builder built
it, from the schema, spec, sort order and properties it was given
([BaseMetastoreCatalog.java#L234-L258](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/BaseMetastoreCatalog.java#L234-L258)).

## Fix

As in #16943, the table builder passes the transaction a function that
builds the replacement from a table (`Transactions` gains package-
private factories that take it, and `TestTables.beginReplace` passes
one). When a commit attempt finds that the table changed since the
transaction began, the transaction rebuilds the replacement on the
refreshed table and applies its updates to it again, as a simple
transaction re-applies its updates. The replace still replaces the
data, schema and partitioning, and keeps everything else as it is: as
it would had it begun after the other writers.

Where #16943 can't rebuild exactly, it commits the replacement as it
began, which drops the other writers' changes. This fix fails the
commit with `CommitFailedException` instead, which no retry of the loop
could get past:

- **the rebuilt replacement differs** in schema (field ids or schema
  id), partition spec, sort order (order id) or format version from the
  one the transaction began with. The files the transaction wrote, and
  the snapshots it made, name those: a sort order id that now means
  another table's order, a format the files weren't written for. A
  concurrent format upgrade lands here: the replace no longer
  downgrades the table;
- **an update can't apply again**: a schema update commits once, on the
  metadata it was created on.

A transaction built without the function (other `TableOperations`, or
the public `Transactions` factories) commits as before, still without
snapshots the table no longer has (C3's fix). A create-or-replace that
finds a table created since still fails as a create does (C9).

After a commit that rebuilt the replacement, the transaction deletes
only the files its updates replaced that no committed snapshot
references, as a simple transaction does: a replay may reuse a file an
earlier attempt replaced.

## What changes for callers

- Two racing replaces with the same definition: as before, the second
  wins; now the first's snapshot stays in history.
- Two whose schema or sort order differ, which rebuild to other ids:
  the second fails, and its caller runs it again. Two `CatalogTests`
  cases, `testConcurrentReplaceTransactionSchema` and
  `testConcurrentReplaceTransactionSortOrderConflict`, expect that,
  except over REST, whose server applies the replace's changes itself.
  The other seven racing-replace cases pass as they were.
- A replace that races any commit no longer erases it.

## Tests

- `TestReplaceTransaction`, on every format version:
  `testReplaceTransactionKeepsConcurrentHistory` (commits to main and a
  branch, a tag and `gc.enabled=false`, all kept);
  `testReplaceTransactionWithConcurrentUpgrade` (fails, the table keeps
  its format); `testReplaceTransactionWithConcurrentSortOrder` (fails);
  `testReplaceTransactionThatCannotApplyAgain` (a schema update in the
  replace; fails, the concurrent property stays). C3's
  `testReplaceTransactionWithConcurrentExpiry` passes as it was.
- `CatalogTests`, for every catalog: `replaceTransactionKeepsConcurrentSnapshot`
  and `replaceTransactionDoesNotRestoreExpiredSnapshot` (from #16943),
  and `replaceTransactionThatCannotApplyAgain` (#16943's test of its
  fallback, inverted: the replace fails, except over REST).
- `TestHiveCreateReplaceTable.testReplaceTableTxnTableModifiedConcurrently`
  now expects the concurrent property kept (from #16943; the fork
  doesn't run the Hive tests).

With the rebuild disabled, the 19 new and changed cases among those
that run on `InMemoryCatalog` and `TestTables` fail. With it,
`TestReplaceTransaction`, `TestCreateTransaction`, `TestTransaction`,
`TestRewriteManifests`, the catalog, in-memory, REST, JDBC and Hadoop
catalog tests, and the full `iceberg-core` test task pass.

## Before a PR

- **Coordinate with #16943.** This is #16943 with its fallback turned
  into a failure, its exactness checked against the replacement the
  transaction began with rather than the transaction's current
  metadata (so a transaction that changes its own schema can't hide a
  difference), and C3's and C9's handling kept. The simplest PR is a
  review of #16943 proposing the failure instead of the fallback.
- **The failure is a behavior change** for racing replaces with
  different definitions, which today end as the second built them. It
  is the choice between committing files under ids that mean something
  else, or erasing another writer's commit, and refusing; upstream may
  prefer to keep the fallback, with a warning, as #16943 does.
- **REST** keeps merging server-side; `UpdateRequirements.forReplaceTable`
  asserts little, so a REST server may still apply a stale replace's
  changes with mismatched ids. Separate issue.

## In fileio-catalog

`TestCatalogFaultProperties` modeled a replace as the table the
transaction saw when it began (A1). It now models it as the table when
the replace commits, with main's data, its deletes and the extra
columns replaced; a replace that can't be rebuilt fails, which the
fuzzer counts as a rejection. Calibrated: with the rebuild disabled in
the fork, the fuzzer catches a replace dropping a concurrent change (a
property; a branch's commit) at try 55. `TestCatalogRaceProperties`
still doesn't race replaces. The canary is
`TestIcebergCoreIssues.aReplaceKeepsWhatOtherWritersCommittedSinceItBegan`;
it asserts only that a commit to another branch survives the replace,
which failing the replace satisfies too.
