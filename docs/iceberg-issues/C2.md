# C2. A retried commit gives a manifest a second row-id range

| | |
|---|---|
| **Affects** | Iceberg 1.10.1 and 1.12.0, and `main` at `524fe9e` (2026-10-16). The files the fix changes have not changed on `main` between `524fe9e` and `9bbee07` (2026-10-18). |
| **Upstream** | Not reported (searched apache/iceberg issues and PRs, 2026-10-16). |
| **Fix** | [`6c6b6fd`](https://github.com/cdouglas/iceberg/commit/6c6b6fd787d1a57ddfc789ce2ec7d0dc32a88582) on [`core-fixes`](https://github.com/cdouglas/iceberg/tree/core-fixes), "Core: Keep the row ids of the manifests a retried commit carries". 5 files, +215/−50. On `main` at `9bbee07`, the main-code changes cherry-pick cleanly. The test file conflicts, because the tests sit next to C7's (see "Before a PR"). |
| **Found by** | fileio-catalog's `TestCatalogFaultProperties`, whose row-lineage check found a data file's `first_row_id` changing. |

## Summary

On a table upgraded to v3, the manifests written before the upgrade get a
`first_row_id` from the first commit after it. Suppose a commit has to
retry because such a commit landed first. The retry then gives those
manifests a second, new row-id range. Their data files' row ids change,
which row lineage forbids.

## Reproduction

```java
Table table = catalog.createTable(ID, SCHEMA);                 // v2
table.newFastAppend().appendFile(file("f0")).commit();
table.updateProperties().set(TableProperties.FORMAT_VERSION, "3").commit();

AppendFiles append = catalog.loadTable(ID).newFastAppend().appendFile(file("f1"));
append.apply();                     // the first attempt, while f0's manifest has no row ids
catalog.loadTable(ID).newDelete().deleteFile(path("missing")).commit(); // assigns f0 row id 0
append.commit();                    // retries on the new base

rowIds(catalog.loadTable(ID));      // f0 is now 2, not 0
```

## Cause

A commit attempt caches what it made from the manifests it saw. Retries
reuse that work. Four caches look manifests up by `ManifestFile` equality,
which for `GenericManifestFile` compares only the path. So on a retry they
return the copy, or the derived manifest, from the earlier attempt, made
before another commit assigned the manifest a `first_row_id`:

1. **`SnapshotProducer.manifestsWithMetadata`**
   ([SnapshotProducer.java#L134](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/SnapshotProducer.java#L134),
   used at [#L328](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/SnapshotProducer.java#L328)).
   For every manifest a commit carries, including the ones it keeps
   unchanged, it returns the first copy seen. `ManifestListWriter` assigns
   a new range to any data manifest whose `first_row_id` is null
   ([ManifestListWriter.java#L139](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/ManifestListWriter.java#L139)).
   Path: any commit, such as a fast append.
2. **`ManifestFilterManager.filteredManifests`**
   ([ManifestFilterManager.java#L93](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/ManifestFilterManager.java#L93),
   read at [#L371](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/ManifestFilterManager.java#L371)).
   It holds kept manifests (the old copy) and rewritten ones. A rewritten
   manifest's existing entries carry the row ids inherited from the copy
   it was read from, here none. Path: a delete, overwrite or row delta.
3. **`ManifestMergeManager.mergedManifests`**
   ([ManifestMergeManager.java#L191](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/ManifestMergeManager.java#L191)).
   Merged bins, keyed by lists of manifests. Path: a merge append.
4. **`BaseRewriteManifests.requiresRewrite`**
   ([BaseRewriteManifests.java#L206-L219](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/BaseRewriteManifests.java#L206-L219)).
   It keeps the earlier attempt's rewritten manifests when every source
   manifest is still current by path. Path: a manifest rewrite.

## Impact

Row lineage breaks: the `_row_id` of an existing row changes, so
downstream consumers see it as a different row. Only v3 tables upgraded
from v2 are affected, and only commits that retry across the first
assignment of row ids after the upgrade. A busy table upgraded while
writers run can hit it.

## Fix

- **`SnapshotProducer`:** don't cache manifests that already have a
  snapshot id. Those need no added metadata, and the cache only ever
  returned them unchanged. Manifests without one (appended by
  `appendManifest`) are still cached, since adding their metadata reads
  the manifest.
- **`ManifestFilterManager`:** cache each result with the `first_row_id`
  of the manifest it was filtered from. On a hit with a different
  `first_row_id`, delete the stale filtered copy if one was written,
  uncount it, and filter again. That logic is shared with
  `cleanUncommitted`, as `uncache`.
- **`ManifestMergeManager`:** the same, keyed by the bin's list of
  `first_row_id`s (`cachedMerge`).
- **`BaseRewriteManifests.requiresRewrite`:** rewrite again when a
  processed manifest's current copy has a different `first_row_id`.

`GenericManifestFile.equals` is unchanged. Cleanup and the cache sets rely
on path equality, and changing it would be a much wider change.

## Tests

In `TestRowLineageAssignment`, one per cache. Each upgrades a v2 table to
v3 and runs an operation's first attempt (`apply()`). Then it assigns row
ids through another table reference, retries, and checks that the
pre-upgrade files keep the assigned row ids:

- `testFastAppendRetryAfterUpgrade`, for `SnapshotProducer`;
- `testDeleteRetryAfterUpgrade`, for `ManifestFilterManager`. It covers a
  rewritten manifest and a kept one.
- `testMergeAppendRetryAfterUpgrade`, for `ManifestMergeManager`;
- `testRewriteManifestsRetryAfterUpgrade`, for `BaseRewriteManifests`.

The four parts of the fix were applied one at a time. Each test kept
failing until its cache's part went in, so each part is needed.

The tests need `random-snapshot-ids`. With `TestTables`' sequential ids,
the retry gets the same snapshot id as the concurrent commit, and
`SnapshotProducer` treats it as a rollback, committing nothing.

## Before a PR

- **Split?** It could be split into four PRs, one per cache, each with its
  test. One PR tells the story better. The `SnapshotProducer` part alone
  fixes the most common case, a fast append.
- **Merge order:** cherry-picked onto `main` without C7, the test file
  conflicts, because C7's test sits next to these. The fix is trivial.
- **Cost on a stale hit:** the retry redoes, for a stale manifest, the
  work the cache would have saved. That happens only on retries that
  cross the first row-id assignment after an upgrade, so it is rare.
- **Checkstyle:** `ManifestMergeManager.createManifest` needed the
  `cachedMerge` helper to stay under the cyclomatic-complexity limit.

## In fileio-catalog

The workaround was the `preUpgrade` map in `TestCatalogFaultProperties`.
It exempted the files a table had at its v3 upgrade from the check that a
row id never changes.
[`dbac28b`](https://github.com/cdouglas/catalog/commit/dbac28becc3cc6d46cd28e1e76c35488eb6e07dc)
removed it, with the canary test. With the exemption removed and without
the fix, the fuzzer finds C2 within 2,000 tries. A new canary,
`TestIcebergCoreIssues.aRetriedCommitKeepsAManifestsRowIds`, asserts
the bug is absent.
