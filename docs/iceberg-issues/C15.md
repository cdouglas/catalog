# C15. An expiry in a transaction deletes files before the transaction commits

| | |
|---|---|
| **Affects** | Iceberg 1.10.0 to 1.12.0, and `main` at `834441b96` (2026-10-21), on every catalog. Earlier releases deferred the deletes, but not correctly either (see "Cause"). |
| **Upstream** | Not reported (searched apache/iceberg's issues, PRs and PR branches, and the issues@ and dev@ lists, 2026-10-21). [#13631](https://github.com/apache/iceberg/pull/13631), "Core: refactor BaseTransaction for extensibility", in 1.10.0, dropped the deferral; [#9183](https://github.com/apache/iceberg/pull/9183), for [#9182](https://github.com/apache/iceberg/issues/9182), had made the deferred deletes run. #13631's review doesn't mention expiry. |

Cherry-picks onto `main` at `834441b96` after C10, C12 and C13 (its tests follow theirs). |
| **Found by** | fileio-catalog's review of Iceberg's commit retry paths for state read before an attempt, 2026-10-20, after the fuzzers found C10 to C14 in that class. Reproduced in `TestRemoveSnapshots`. |

## Summary

`Transaction.expireSnapshots()` returns an expiry whose `commit()`
commits to the transaction and then deletes the files of the snapshots
it removed: their manifest lists, and the manifests and data files no
remaining snapshot reaches. It does so before the transaction commits.

- If the transaction then fails, the table keeps those snapshots, but
  their manifest lists are gone.
- If the transaction retries after another writer's commit, it commits
  the expiry again on the refreshed table, which may keep a snapshot the
  first attempt removed, such as one the other writer tagged (C10). The
  snapshot stays, and its files are gone.

## Reproduction

```java
table.newFastAppend().appendFile(FILE_A).commit();
Snapshot s1 = table.currentSnapshot();
table.newFastAppend().appendFile(FILE_B).commit();

Transaction txn = table.newTransaction();
txn.expireSnapshots().expireOlderThan(now).retainLast(1).commit();
new File(s1.manifestListLocation()).exists();               // false: deleted already

catalog.loadTable(ID).manageSnapshots().createTag("t", s1.snapshotId()).commit();
txn.commitTransaction();                                     // retries, keeps s1 for the tag

catalog.loadTable(ID).snapshot(s1.snapshotId()).allManifests(io);
// NotFoundException: the manifest list of s1
```

With a schema update after the expiry in the same transaction, and a
commit by another writer before `commitTransaction`, the transaction
fails with `CommitFailedException`, and s1 is left without its manifest
list in the same way.

## Cause

`BaseTransaction.expireSnapshots()` creates the expiry over the
transaction's operations
([BaseTransaction.java#L228-L230](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/BaseTransaction.java#L228-L230))
through `appendUpdate`, which defers an update's deletes to the
transaction only for a `SnapshotUpdate`
([#L123-L135](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/BaseTransaction.java#L123-L135)).
`RemoveSnapshots` is not one. Its `commit()` cleans up as soon as its
commit to the transaction returns
([RemoveSnapshots.java#L360-L381](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/RemoveSnapshots.java#L360-L381)),
with the table's `FileIO`, and a transaction that retries commits it
again ([BaseTransaction.java#L438-L453](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/BaseTransaction.java#L438-L453)).

Before #13631, `expireSnapshots()` called `deleteWith(enqueueDelete)`,
so the deletes waited for the transaction's commit. That was not right
either: a failed transaction's `cleanUp()` deletes every enqueued file
([#L415-L421](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/BaseTransaction.java#L415-L421)),
the expiry's included, and a retry kept the files the first attempt
enqueued. Restoring that call would not fix either case.

## Impact

A transaction that expires snapshots alongside other changes, and fails
or retries, leaves the table with snapshots it cannot read. Time travel,
rollback and incremental reads to them fail, as does a reachable-files
cleanup of a later expiry that reads their manifest lists (logged since
C13). Spark's `expire_snapshots` procedure does not use a transaction;
callers of the Java API that do, and catalogs that wrap an expiry in a
transaction, hit it.

## Fix

The transaction's expiry defers its cleanup, and the transaction runs it
once it has committed, for every transaction type, comparing the
metadata the expiry's last attempt started from with what the
transaction committed:

```java
@Override
public ExpireSnapshots expireSnapshots() {
  // its files are cleaned up once the transaction commits, from what it committed
  return appendUpdate(new RemoveSnapshots(transactionOps).cleanUpOnceTransactionCommits());
}
```

A failure of that cleanup is logged: the transaction has committed. An
incremental cleanup the caller asked for that cannot run still fails
when the expiry is committed to the transaction, as before.

## Tests

In `TestRemoveSnapshots`, on every format version:

- `testTransactionExpiryDeletesNothingWhenTheTransactionFails`, with
  incremental cleanup and without: the second reproduction. The expired
  snapshot's manifest list is there after the failure.
- `testTransactionExpiryRetriedAfterConcurrentTag`, with reachable
  cleanup (the tag leaves a snapshot outside main's ancestry, which
  incremental cleanup refuses): the first reproduction. The tagged
  snapshot keeps its manifest list, and the one the retry still expires
  loses it.

All 12 cases that run fail without the fix. With it, `TestRemoveSnapshots`,
`TestTransaction`, `TestReplaceTransaction`, `TestCreateTransaction` and
the full `iceberg-core` test task pass.

## Before a PR

- **Hooks.** `BaseTransaction` and `RemoveSnapshots` meet through two
  package-private methods. A reviewer may prefer an interface that other
  updates with post-commit work could implement.
- **Why not `deletedFiles`.** The transaction's enqueued deletes are
  files its updates wrote and did not commit, garbage if the transaction
  fails. An expiry's are the opposite: garbage only if it commits. The
  two need different handling, which is why the fix doesn't restore the
  old `deleteWith(enqueueDelete)`.
- **Regression.** Worth pointing at #13631 in the PR: before it, the
  common case (the transaction commits on its first attempt) deleted
  after the commit. #9183's review states the intent; amogh-jahagirdar
  (member): "If there are no committed files (which would be expected for
  a transaction with just `ExpireSnapshots`) but there are files to
  cleanup (which would be expected for `ExpireSnapshots` again) then we
  should proceed with the file removal."

## In fileio-catalog

No workaround: no fuzzer runs an expiry inside a transaction against a
concurrent writer. `TableScript` runs expiries and transactions, in
single-writer and differential properties that would not see files
deleted early. The canary is
`TestIcebergCoreIssues.aTransactionsExpiryDeletesFilesOnlyOnceItCommits`.
It asserts only that a snapshot the transaction's retry keeps can still
be read.
