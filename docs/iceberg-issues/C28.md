## Summary

A JDBC commit swaps the table's row with a conditional UPDATE
(`... WHERE metadata_location = <base's>`), through `JdbcClientPool`,
which runs a statement again once after its connection fails. If the
UPDATE committed but its reply was lost, the second run matches no row,
and `JdbcTableOperations` reports a conflict: a CommitFailedException.
The table now is that commit. CommitFailedException is a
`CleanableFailure`, so once Iceberg's retries are spent the snapshot
producer deletes the commit's manifest list and manifests, which the
table's current snapshot names.

When the second run's connection fails too, the pool rethrows the first
failure and the commit fails with an UncheckedSQLException, a definite
failure, though the first run may have committed. A create whose INSERT
committed but whose reply was lost fails the same way: its second run
hits the table's key, and the pool reports the first failure.

## Reproduction

`TestJdbcCatalog` on the fork runs each case over a client pool whose
connections fail as told (SQLState 08006), on a SQLite file database:

| Case | 1.12.0 | Fixed |
|---|---|---|
| An append's UPDATE commits, its reply is lost (`commit.retry.num-retries=0`) | CommitFailedException; the cleanup deletes the committed snapshot's files | commits |
| A schema update's UPDATE commits, its reply is lost, and the second run's connection fails | UncheckedSQLException ("Unknown failure"); the column is there | commits |
| The connection fails before the UPDATE runs, on both runs | UncheckedSQLException | CommitStateUnknownException |
| A create's INSERT commits, its reply is lost | UncheckedSQLException; the table exists | creates |

## Cause

`ClientPoolImpl.run` reconnects and runs the action again when it fails
with a connection exception, and `JdbcClientPool` takes SQLStates that
mean a connection failed (and 40001, a serialization failure, which did
not commit) as one. Running a conditional UPDATE again is safe only if
the first run did not commit, which a lost reply cannot tell. A run that
matches no row is then indistinguishable from a conflict, and
`JdbcTableOperations.updateTable` takes it for one. The metastores check
a commit's status after an ambiguous failure (`checkCommitStatus`); JDBC
never did, and never reported CommitStateUnknownException.

## Impact

- With no retries left (`commit.retry.num-retries=0`, or the last one),
  the cleanup deletes the files of the table's current snapshot: the
  table can no longer be planned.
- With retries left, the retry refreshes and finds its own snapshot
  committed (`SnapshotProducer` keeps its snapshot id), and takes the
  "rollback" branch: no change if the head is still its snapshot, and if
  another writer committed on top, it moves the branch back over that
  commit (#18743). A validated operation's retry may instead fail
  validation against its own snapshot, a ValidationException, also
  cleanable (code reading, untested).
- Updates that are not retried (a schema update) report a failure for a
  change that landed; a caller that retries applies it twice.
- An UncheckedSQLException is not cleanable, so no files are deleted, but
  the commit is reported failed rather than unknown, and a caller's
  retry duplicates it.

## Fix

In `JdbcTableOperations`:

- An UPDATE that matches no row checks the commit's status strictly
  (`checkCommitStatusStrict`): the table naming the commit's metadata
  file, now or in its metadata log, is a commit; not naming it is a
  conflict (CommitFailedException), since the UPDATE has finished and no
  pending run can commit; a status that cannot be read is unknown
  (CommitStateUnknownException). This is #18745's change.
- An UPDATE or a create's INSERT whose connection fails on every run the
  pool makes checks it as the metastores do after an ambiguous failure
  (`checkCommitStatus`): naming the file is a commit, and anything else is
  unknown, since a statement whose connection failed may still have
  committed.

Views (`JdbcViewOperations.updateView`), renames, drops and unregisters
are left as they are: a view's metadata keeps no log of earlier metadata
files to check, and the others are not commits of a metadata file.

## Tests

`TestJdbcCatalog`: `testCommitWhoseUpdateReplyIsLost`,
`testCommitWhoseConnectionFailsAfterItsUpdateCommitted`,
`testCommitWhoseConnectionFailsBeforeItsUpdateIsUnknown`,
`testCreateWhoseInsertReplyIsLost`, over `FaultyClientPool` (a
`JdbcClientPool` whose connections fail as `Faults` says). Each fails on
1.12.0 and on `core-fixes` without the fix; the JDBC suites (341 tests)
pass with it.

## Before a PR

#18745 is open with the strict check on a zero-row UPDATE. Offer this
fix's other cases there (a connection that fails on every run reported
as unknown, not as an SQL failure; a create whose INSERT reply is lost),
and its tests, rather than a second PR. The views, renames, drops and
unregisters are a follow-up; so is whether `JdbcClientPool` should run a
write again at all (Hive's pool does not: `retryByDefault` false).

## In fileio-catalog

No workaround: FileIOCatalog does not use JDBC. The canary
`TestIcebergCoreIssues.aJdbcCommitWhoseReplyIsLostCommits` runs Iceberg's
JdbcCatalog on SQLite (test dependency `sqlite-jdbc`). catalog-bench's JDBC
baseline runs Iceberg 1.12.0 with performance fixes only (the fork's
branch `perf`), so it keeps this bug; its runs inject no connection
failures.
