## Summary

An expiry removes the refs it expires and then the snapshots it doesn't
keep. A REST client sends both as updates; the server applies them to
the table's current metadata. Removing snapshots from metadata also
removes, silently, any ref still pointing to them. When another writer
has set a ref on a removed snapshot since the client's read, that ref
goes with it:

- a tag another writer created on the snapshot disappears, and so does
  the snapshot;
- after another writer rolled main back to the snapshot, main itself is
  removed, and the table has no current snapshot.

Run in either order, the tag keeps its snapshot, or main stays at its
target, or the second operation fails.

## Reproduction

```java
// the client's expiry, computed on base, removes s1
TableMetadata base = ops.current();
catalog.loadTable(ID).manageSnapshots().createTag("t", s1).commit();   // another writer

CatalogHandlers.updateTable(catalog, ID, UpdateTableRequest.create(ID,
    UpdateRequirements.forUpdateTable(base, updates), updates));   // RemoveSnapshots(s1)

catalog.loadTable(ID).refs();     // no "t"
```

With `rollbackTo(s2)` by the other writer, and an expiry that removes
s2, main is removed: `currentSnapshot()` is null.

## Cause

`MetadataUpdate.RemoveSnapshots.applyTo` calls the builder's
`removeSnapshots`
([MetadataUpdate.java#L349](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/MetadataUpdate.java#L349)),
which removes the refs that point to a removed snapshot
([TableMetadata.java#L1461-L1469](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/TableMetadata.java#L1461-L1469)).
The expiry computed what to remove from the refs it saw. No requirement
can say that no new ref points to a snapshot, and `UpdateRequirements`
derives none from a snapshot removal
([UpdateRequirements.java#L96-L112](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/UpdateRequirements.java#L96-L112)).

## Impact

A periodic expiry over REST that races a tag, such as a release tag on a
recent snapshot near the retention cutoff, drops the tag and the
snapshot; both writers see success. One that races a rollback of main
leaves the table without a current snapshot.

## Fix

Applying a `RemoveSnapshots` update fails while a ref points to one of
its snapshots, with `RetryableValidationException`:

```java
Builder removeUnreferencedSnapshots(Collection<Long> idsToRemove) {
  for (Map.Entry<String, SnapshotRef> ref : refs.entrySet()) {
    RetryableValidationException.check(
        !idsToRemove.contains(ref.getValue().snapshotId()),
        "Cannot remove snapshot %s: ref %s points to it",
        ref.getValue().snapshotId(),
        ref.getKey());
  }

  return removeSnapshots(idsToRemove);
}
```

`CatalogHandlers` returns that exception to the client as a
`CommitFailedException`, without retrying on the server
([rest/CatalogHandlers.java#L632](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/rest/CatalogHandlers.java#L632)).
The client's expiry retries on refreshed metadata (C10) and keeps the
snapshot. `TableMetadata.Builder.removeSnapshots` still removes the
refs, for its other callers.

## Tests

`TestTableMetadata.testRemovingAReferencedSnapshotIsRetryable`: the
removal fails while a tag points to the snapshot, and succeeds once the
tag's removal precedes it, as in an expiry's updates. It fails without
the fix. With it, `TestTableMetadata`, `TestMetadataUpdateParser`, the
REST, catalog and in-memory catalog tests, `TestRemoveSnapshots`,
`TestReplaceTransaction` and the full `iceberg-core` test task pass.

## Before a PR

- **Not a new report:** reply on the dev@ thread. Its open objection, from
  Tobias: "A catalog does not know if the received update was produced by
  running ExpireSnapshots or if it is an explicit call, changing the
  behavior to fail instead of cleaning up referenced branches means the
  REST catalog diverges." He proposed a flag on `RemoveSnapshots`
  instead. amogh-jahagirdar (member) first answered that "This situation
  shouldn't happen", and didn't reply to the clarification.
- **Other clients.** The check assumes a client removes the refs of the
  snapshots it removes first, as Java's `RemoveSnapshots` does. Check
  PyIceberg and the other clients that send `remove-snapshots`.
- **The alternative,** requiring every ref of the client's metadata to
  be unchanged, would make an expiry conflict with every commit to main,
  and still miss new refs.

## In fileio-catalog

`FileIOCatalog.commitTransaction` applies a catalog transaction's
updates the same way, so a transaction with an expiry had the same gap.
With the fix it fails with the `RetryableValidationException`, a
`ValidationException`, and the caller runs it again. The canary is
`TestIcebergCoreIssues.aRemovalAppliedToNewerMetadataKeepsAConcurrentTag`.
It asserts only that the tag and its snapshot survive.
