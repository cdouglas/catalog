## Summary

`ExpireSnapshots` (`RemoveSnapshots`) works out which snapshots to remove
from the table's metadata, and commits that. If the commit fails with
`CommitFailedException`, because another writer committed first, it
retries on the refreshed metadata. But it kept, in the set of ids to
remove, the snapshots its earlier attempts chose, and added to them. On
the retry that set can name snapshots the refreshed metadata no longer
has, or now keeps:

- Another writer expired the same snapshots: the retry fails with
  `IllegalArgumentException: arraySize cannot be negative`, when it asks
  to remove more snapshots than the table has.
- Another writer tagged one of them, or moved a branch to it: the retry
  fails with `IllegalArgumentException: Cannot expire ... Still referenced
  by refs`, though the snapshot should simply be kept.

Either way an expiry that should commit, keeping what the refreshed table
needs, fails instead.

## Reproduction

```java
Table table = catalog.createTable(ID, SCHEMA);
table.newFastAppend().appendFile(file("a")).commit();
table.newFastAppend().appendFile(file("b")).commit();
table.newFastAppend().appendFile(file("c")).commit();
long now = System.currentTimeMillis();

// table's operations, wrapped so that its first commit runs, just before it,
// another writer's expiry of the same snapshots
TableOperations racing = ...;
new BaseTable(racing, "t").expireSnapshots()
    .expireOlderThan(now).retainLast(1).commit();
// IllegalArgumentException: arraySize cannot be negative but was: -1
```

The first attempt chooses the two older snapshots. The other writer
expires them, so the commit conflicts. The retry refreshes to a table with
one snapshot and asks to remove two.

## Cause

`idsToRemove` is a field. `expireSnapshotId` adds the ids a caller names.
`internalApply`, which runs on each attempt, adds to the same set every
snapshot that attempt's metadata does not retain
([RemoveSnapshots.java#L233-L237](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/RemoveSnapshots.java#L233-L237)),
and checks that none of the set is still referenced
([#L215-L221](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/RemoveSnapshots.java#L215-L221)).
A retry
([#L360-L373](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/RemoveSnapshots.java#L360-L373))
starts from what the earlier attempts left there.
`TableMetadata.Builder.removeSnapshots` sizes its list of kept snapshots
as the table's count less the ids to remove
([TableMetadata.java#L1443-L1444](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/TableMetadata.java#L1443-L1444)),
which is negative once the set names more snapshots than the table has.

## Impact

An `expire_snapshots` job that conflicts with another expiry of the same
table fails, and so does one that conflicts with a commit that tags or
branches an old snapshot. Neither leaves the table wrong; the job just
fails where a retry should have succeeded. By the same cause, a retry
could remove a snapshot the refreshed metadata keeps for a reason the ref
check does not see, such as a branch whose `min-snapshots-to-keep` was
raised in between (read from the code, not tested).

## Fix

The set of ids a caller names stays as it is. Each attempt works out what
to remove on its own metadata: the snapshots it has that the caller named
or that it does not retain.

```java
// computed on each attempt's metadata: a retry after a conflict must not remove a snapshot
// that an earlier attempt's metadata did not retain but this one does, nor one that is gone
Set<Long> snapshotsToRemove =
    base.snapshots().stream()
        .map(Snapshot::snapshotId)
        .filter(snapshot -> idsToRemove.contains(snapshot) || !idsToRetain.contains(snapshot))
        .collect(Collectors.toSet());
updatedMetaBuilder.removeSnapshots(snapshotsToRemove);
```

A named snapshot that another writer expired in the meantime is gone, as
the caller asked; it no longer counts. The ref check still applies to the
snapshots the caller names.

## Tests

In `TestRemoveSnapshots`, on every format version, with incremental
cleanup and without:

- `testRetryAfterConcurrentExpiry`: the reproduction above. The expiry
  commits, and the table keeps only its current snapshot.
- `testRetryAfterConcurrentTag`: another writer tags an older snapshot
  between the expiry's attempts. The expiry commits; the tagged snapshot
  stays, the other old one goes.

All 16 cases fail on 1.12.0, half with each message above. With the fix,
`TestRemoveSnapshots` (536 cases) and the full `iceberg-core` check pass.

## Before a PR

- **The capacity hint.** `TableMetadata.Builder.rewriteSnapshotsInternal`
  could also guard its list size (`Math.max(0, ...)`), so that an id the
  table does not have never fails the builder. The fix doesn't need it,
  but a reviewer may prefer both.
- **Named ids that are gone.** The fix drops a named snapshot that another
  writer expired since: it is gone, as asked. Failing instead would be
  stricter, but a named id the table never had already removes nothing
  (when the table has enough snapshots not to fail as above).

## In fileio-catalog

There was no workaround: the fuzzer counts any exception but the
expected rejections as unexpected without an injected fault. The canary
is `TestIcebergCoreIssues.anExpiryRetriesAfterAConcurrentExpiry`. It wraps
an `InMemoryCatalog` table's operations to run another writer's expiry
just before the first commit, and asserts only that the expiry commits
and keeps the current snapshot.
