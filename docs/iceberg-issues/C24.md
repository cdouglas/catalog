## Summary

In a v3 table, a commit that removes a data file removes its deletion
vector (DV) too: `MergingSnapshotProducer` passes the removed files to
the delete manifests' `ManifestFilterManager`, which drops each DV that
names one. Before opening a delete manifest, the filter asks whether it
can contain anything to drop. That check looked at the partitions of the
explicitly deleted files first and, if there were any, answered with
them alone: the removed data files were consulted only when there were
none. Two ways to get there:

- **A row delta that removes a data file and, explicitly, a delete file
  of another partition.** The manifest holding the removed file's DV is
  outside that partition, and is never opened.
- **A commit that retries.** The filter adds every file it drops to its
  set of deleted files, but not their partitions. After a first attempt
  that dropped the DV, the set is not empty, its partitions are, and the
  retry opens no delete manifest it hasn't filtered before. If another
  writer rewrote the DV's manifest in between (a row delta that merged
  delete manifests, with `commit.manifest.min-count-to-merge` reached),
  the new manifest keeps the DV.

The DV is left live, naming a data file the table no longer has.

## Reproduction

```java
// v3, commit.manifest.min-count-to-merge=2
table.newFastAppend().appendFile(FILE_A).commit();
table.newFastAppend().appendFile(FILE_B).commit();
table.newRowDelta().addDeletes(dvForFileA).commit();

// another writer's equality delete lands just before the delete's first commit, merging the
// DV's manifest into a new one
racingTable.newDelete().deleteFile(FILE_A.location()).commit();   // retries, and commits

// the table's delete files: the equality delete, and FILE_A's DV
```

## Cause

`ManifestFilterManager.canContainDroppedFiles`
([ManifestFilterManager.java#L438-L448](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/ManifestFilterManager.java#L438-L448))
returns the partition check of the explicitly deleted files when there
are any, before it reaches `removedDataFilePaths`.
`filterManifests` adds the files it dropped to `deleteFiles`
([#L232](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/ManifestFilterManager.java#L232)),
but `deleteFilePartitions` only records explicit deletes
([#L176-L188](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/ManifestFilterManager.java#L176-L188)).

## Impact

A dangling DV applies to a data file added again under the same path,
as a cherry-pick of an older snapshot does: rows are deleted that the
new file's writer never deleted. A second DV for that file, added
later, makes the table's deletes fail to index. Until then the DV is
metadata that no scan uses, counted in the snapshot's totals.

## Fix

As #18197's first commit does: check each condition on its own, so the
removed data files are consulted whatever the explicit deletes are. Its
second commit, which also opens a delete manifest whose only files to
drop are older than the minimum data sequence number, is left out: a
merging commit drops such files whenever it rewrites the manifest for
another reason, and #11131 chose not to rewrite one for them alone.

```java
if (!deleteFiles.isEmpty()
    && ManifestFileUtil.canContainAny(manifest, deleteFilePartitions, specsById.get())) {
  return true;
}

// a deletion vector of a removed data file may be in any delete manifest
if (!removedDataFilePaths.isEmpty()) {
  return true;
}
```

## Tests

- `TestManifestFilterManager` (new, from #18197, adapted to C4's spec
  supplier). Its test of the second commit is turned around:
  `manifestsWithOnlyObsoleteDeleteFilesAreNotOpened` asserts that such a
  manifest is not read.
- `TestRowDelta.testRemovingAFileAndAnotherPartitionsDeleteRemovesTheFilesDV`
  and `testDeleteRetriedAfterConcurrentMergeRemovesTheFilesDV`, on v3
  and v4, on `main` and on a branch: the two cases above.

Without the fix, 10 of the 24 cases fail. With it, `TestRowDelta`,
`TestDeleteFiles`, `TestRewriteFiles` and the full `iceberg-core` test
task pass.

## Before a PR

- **Review #18197** rather than open another PR. Propose its first
  commit alone, and ask to drop the second, which reverses #11131's
  deliberate choice (amogh-jahagirdar's rationale on #11131, 2024-12-04;
  rdblue on #10962, 2025-02-04). Its description counts the obsolete
  delete files the second commit drops as dangling DVs, which they are
  not: they apply to no live row. Offer the two `TestRowDelta` cases, the
  retry one in particular, which #18197's description doesn't mention.
- **Stacked on #18197:** [#18154](https://github.com/apache/iceberg/pull/18154) (open) prunes the delete manifests on
  this path by partition, including by the removed data files'
  partitions. It would narrow this fix's "any delete manifest" when data
  files are removed; check the two together.

## In fileio-catalog

No workaround: the fuzzer's model removes a data file's DV with it. The
canary is `TestIcebergCoreIssues.aRemovedDataFilesDeletionVectorIsRemovedOnRetry`;
it asserts only that the retried delete leaves no DV naming the file.
