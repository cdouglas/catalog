## Summary

A commit drops the delete files older than the minimum data sequence
number of the table's live data files, since they can no longer apply to
any row (`MergingSnapshotProducer`'s delete age-off).

The minimum is taken over the data manifests the commit keeps from its
parent, and not over the data files it adds. A `RewriteFiles` that
commits its new files with an older data sequence number
(`dataSequenceNumber`, or `rewriteFiles(..., sequenceNumber)`) adds data
that a delete newer than that number still applies to. Spark's
`rewrite_data_files` does this by default (`use-starting-sequence-number`).

When no kept data file is older than the delete, the commit drops the
delete, and the rows it deleted from the rewritten file come back.

## Reproduction

```java
// v2
table.newFastAppend().appendFile(F).commit();                 // seq 1
long start = table.currentSnapshot().sequenceNumber();         // a compaction reads F here
table.newRowDelta().addDeletes(equalityDeleteOfFsRows).commit(); // seq 2
table.newFastAppend().appendFile(K).commit();                  // seq 3, unrelated

table.newRewrite()
    .dataSequenceNumber(start)   // G keeps F's data sequence number, 1
    .deleteFile(F)
    .addFile(G)
    .commit();

// the rewrite removed the equality delete (removed-equality-delete-files=1),
// so G's rows that it deleted are live again
```

## Cause

[MergingSnapshotProducer.java#L1026-L1035](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/MergingSnapshotProducer.java#L1026-L1035)
computes the minimum over `filtered`, the parent's data manifests after
the commit's deletes, starting from `base.lastSequenceNumber()`. The
manifests of the new data files are added only later, so their data
sequence numbers never reach the minimum:
- F's manifest has no live entry left, so the fold skips it.
- K's manifest has a minimum of 3.

So the minimum is 3, and the delete at 2 is dropped although it applies
to G at 1.

A retry gets there more easily. The minimum is recomputed on the
refreshed parent, so a concurrent commit that removes the last older
data file (#10312's timeline) drops the delete on the retry, though the
first attempt kept it.

## Impact

Deleted rows reappear after a compaction, with no error. An equality
delete or a position delete applies to the rewritten file, because the
rewrite kept the data sequence number the compaction read at, and
nothing else still holds the delete. Engines that compact with the
starting sequence number while deletes stream in (#10312) hit it.

## Fix

Include the added files' data sequence number in the minimum, as #10962
does:

```java
if (newDataFilesDataSequenceNumber != null && addsDataFiles()) {
  // new data files that keep an older data sequence number still need the deletes after it
  minDataSequenceNumber = Math.min(minDataSequenceNumber, newDataFilesDataSequenceNumber);
}
```

Only `RewriteFiles` sets `newDataFilesDataSequenceNumber`; other
producers' added files take the commit's sequence number, which is never
older than a live delete.

## Tests

`TestRewriteFiles.testRewriteWithOldSequenceNumberKeepsTheDeletesAfterIt`
runs on v2, v3 and v4, on `main` and on a branch: the case above.

Without the fix, all 6 cases fail. With it, these pass:
`TestRewriteFiles`, `TestRowDelta`, `TestSequenceNumberForV2Table`,
`TestManifestFilterManager`, `TestMergeAppend`, `TestDeleteFiles`,
`TestOverwriteWithValidation`, `TestReplacePartitions` and the core
`actions` tests (1,566 tests).

## Before a PR

- **Review #10962** rather than open another PR. Propose its age-off half
  alone, since the maintainers accepted it and rejected the other half.
  Offer this test, which needs neither a retry nor the manifest-filter
  change.
- Its `minDataSequenceNumber` computes a minimum over `addedDataFiles()`
  that it doesn't use, and compares a long with `Integer.MAX_VALUE`. The
  one-line form here avoids both.
- **Related, in this fork:** C24's fix had taken #18197's second commit,
  which also opens delete manifests that hold only aged-off deletes: the
  eager cleanup amogh-jahagirdar and rdblue opposed in this thread. It
  dropped that commit on 2026-10-24, so the two fixes agree with the
  maintainers' position.

## In fileio-catalog

No workaround to remove: the fuzzers' `RewriteFiles` never set a data
sequence number. The conflict-encoding oracle (`TestRebaseProperties`)
will, because a compaction's retry is one of its references. The canary
is `TestIcebergCoreIssues.aRewriteWithAnOlderSequenceNumberKeepsTheDeletesItNeeds`.
