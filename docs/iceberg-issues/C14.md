# C14. A cherry-pick of a snapshot expired since it was picked fails with a NullPointerException

| | |
|---|---|
| **Affects** | Iceberg 1.12.0, and `main` at `3738f4a97` (2026-10-20), on every catalog. |
| **Upstream** | Not reported (searched apache/iceberg issues and PRs, 2026-10-20). |
| **Fix** | [`b1f2e01`](https://github.com/cdouglas/iceberg/commit/b1f2e01e4d761d2725adbcd3a8896b6f7ada07ab) on [`core-fixes`](https://github.com/cdouglas/iceberg/tree/core-fixes), "Core: Fail a cherry-pick of a snapshot expired since it was picked". 2 files, +47. Cherry-picks onto `main` at `3738f4a97` after C6 and C8 (its tests follow theirs). |
| **Found by** | fileio-catalog's `TestCatalogFaultProperties`, 2026-10-20, at try 25,453 of a 30,000-try run: a cherry-pick of a staged snapshot, preempted by another writer's expiry that removed it, failed with `NullPointerException: Cannot invoke "Snapshot.summary()" because "snapshot" is null`, with no fault injected. |

## Summary

`ManageSnapshots.cherrypick(id)` checks that the snapshot exists when the
pick is set up. Each commit attempt refreshes the table, and by then
another writer may have expired the snapshot: a staged (write-audit-
publish) snapshot is on no ref, so an expiry removes it like any old
snapshot. The attempt then fails with a `NullPointerException`:

- a pick that adds the snapshot's files fails in its validation, which
  reads the snapshot's summary for its `wap.id`;
- a pick that fast-forwards the branch to the snapshot returns a null
  snapshot to commit.

## Reproduction

```java
table.newAppend().appendFile(FILE_A).commit();
table.newAppend().appendFile(FILE_B).stageOnly().commit();   // staged, on no ref
long staged = ...;                                            // its id
ManageSnapshots pick = table.manageSnapshots().cherrypick(staged);

catalog.loadTable(ID).expireSnapshots().expireSnapshotId(staged).commit();   // another writer

pick.commit();
// NullPointerException (a fast-forward here; with a commit on main in between, the same
// in WapUtil.stagedWapId)
```

## Cause

The pick looks the snapshot up once, when it is set up
([CherryPickOperation.java#L73](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/CherryPickOperation.java#L73)),
and keeps it. `apply()` refreshes
([#L185-L186](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/CherryPickOperation.java#L185-L186))
but does not look again: a fast-forward returns
`base.snapshot(id)`, null once the snapshot is gone
([#L199](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/CherryPickOperation.java#L199)),
and `validate` passes the id to `WapUtil.validateWapPublish`
([#L169](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/CherryPickOperation.java#L169)),
which reads the summary of the snapshot it finds there
([WapUtil.java#L50-L52](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/util/WapUtil.java#L50-L52)).

## Impact

A write-audit-publish job whose publish races an expiry fails with a
`NullPointerException`, which says nothing of what happened. The table
is unchanged. Run after the expiry, the pick fails cleanly ("Cannot
cherry-pick unknown snapshot ID").

## Fix

`apply()` checks, on the metadata it has just refreshed, that the table
still has the picked snapshot, and fails with `ValidationException`
otherwise:

```java
// another writer may have expired the picked snapshot since it was picked
ValidationException.check(
    base.snapshot(cherrypickSnapshot.snapshotId()) != null,
    "Cannot cherry-pick snapshot %s: the table no longer has it",
    cherrypickSnapshot.snapshotId());
```

## Tests

In `TestWapWorkflow`, on every format version:

- `testCherrypickOfASnapshotExpiredSincePicked`: a commit on main between
  the stage and the pick, so the pick adds the snapshot's files.
- `testFastForwardToASnapshotExpiredSincePicked`: the reproduction, a
  fast-forward.

Both fail with `ValidationException` and leave the table as it was. All
8 cases fail on 1.12.0 with the `NullPointerException`. With the fix,
`TestWapWorkflow` (80 cases) and the full `iceberg-core` test task pass.

## Before a PR

- **Message.** The set-up check says "Cannot cherry-pick unknown
  snapshot ID"; the new one says the table no longer has it, which tells
  a caller it was there. A reviewer may prefer one message.
- **Retry.** `ValidationException` is not retried, which is right: no
  later attempt can find the snapshot.

## In fileio-catalog

No workaround: the fuzzer counted the exception as unexpected. With the
fix, the pick's `ValidationException` is a rejection, and the fuzzer
checks that the catalog did not change. The canary is
`TestIcebergCoreIssues.aCherryPickOfASnapshotExpiredSincePickedFailsCleanly`.
It asserts only that the pick does not fail with a
`NullPointerException`.
