## Summary

Two writers that set a key a namespace doesn't have yet both read its
properties, find the key missing, and INSERT it. The second INSERT fails on
the table's primary key (catalog, namespace, key), and `setProperties`
throws `UncheckedSQLException`, though run one after the other both sets
succeed and the last writer's value stands. A writer that sets a key the
namespace has, while another removes it, UPDATEs a row that is gone: it
throws `IllegalStateException` ("Failed to update: 0 of 1 succeeded").
Before that, its INSERT of the set's new keys has already committed, so
part of the set lands, and the caller is told it failed.

## Reproduction

Two `JdbcCatalog`s on one SQLite database. The first's connections run
the second's write just before they prepare their first statement that
writes namespace properties:

- The second sets `k` on a namespace without it, and the first's set of
  `k` fails with the `UncheckedSQLException` above.
- The second removes `k` from a namespace with it, and the first's set of
  `k` and a new `n` fails with the `IllegalStateException`. `n` is set
  anyway.

`TestJdbcCatalog`'s tests below do this, as does fileio-catalog's canary.

## Cause

```java
Map<String, String> startingProperties = fetchProperties(namespace);
...
for (String key : properties.keySet()) {
  if (startingProperties.containsKey(key)) {
    updates.put(key, value);
  } else {
    inserts.put(key, value);
  }
}

if (!inserts.isEmpty()) {
  hadInserts = insertProperties(namespace, inserts); // a statement of its own
}

if (!updates.isEmpty()) {
  hadUpdates = updateProperties(namespace, updates); // another
}
```

The read and each write run on the pool's connections in auto-commit
mode, so nothing holds the split between INSERT and UPDATE true until
the writes run. `insertProperties` doesn't handle the primary key's
violation, and `updateProperties` throws when the UPDATE matches fewer
rows than it sets.

## Impact

It's moderate for a service. Concurrent `ALTER NAMESPACE ... SET
PROPERTIES` on one namespace is rare from engines, but a REST server on
`JdbcCatalog` takes property updates from many clients (Iceberg's
test fixture, `RESTCatalogServer`, is one). Such a server reports the failure as
a 500, not as a conflict. The removal race also breaks the API's
contract that a set lands whole or not at all. Nothing is lost: a retry
by the caller succeeds. FileIOCatalog and Polaris treat such a race as a
conflict, while JDBC's set is last-writer-wins by design. So the bug is
the spurious failure, not the semantics.

## Fix

`core-fixes` d4cc466 runs the INSERT and the UPDATE in one transaction.
When the INSERT fails on the primary key (`JdbcUtil.isConstraintViolation`),
or the UPDATE matches fewer rows than it sets, the transaction is rolled
back and the set tries again on a fresh read. It makes up to five
attempts, as many as a table commit makes by default
(`commit.retry.num-retries` 4, plus the first). After that it throws
`CommitFailedException`. A set lands whole or not at all, and sets of
one key that race end with the last writer's value, as they do without a
race.

The fix uses no upsert syntax, so rdblue's objection in #4220 doesn't
apply: the statements are the same generic SQL as before.

- **Postgres:** under READ COMMITTED, its default, an INSERT racing
  another's uncommitted insert of the key waits for it, then fails on
  the key. An UPDATE of a row deleted since skips it. The fix detects
  both.
- **Lost replies:** `JdbcClientPool` reconnects and reruns the whole
  transaction after a connection failure. If the first run committed
  but lost its reply, the rerun's INSERT fails on the key, and the next
  attempt updates to the same values.
- **Deadlocks:** a deadlock, 40001 (such as MySQL's among three writers
  inserting one key), is one of the pool's default retryable states, so
  it reruns the transaction too.

## Before a PR

- **Not reported:** open an issue with the reproduction, citing #4220's
  review, or go straight to a PR; the change is small.
- **Retry bound:** five attempts, then `CommitFailedException`, is a
  choice. Each attempt that fails means another writer changed one of
  these keys, so the system as a whole makes progress, and an unbounded
  loop would also do. A property for the bound is the other option (#18539
  made the JDBC metadata refresh's retries configurable).
- **Cherry-picking:** onto `main` at `e70a2efcd0`, the main change
  applies on its own. The test file's imports need a one-line merge
  unless C28's commit, which adds an import beside them, goes first.
- **A sibling:** `createNamespace` has the same shape, which we found by
  reading the code and haven't tested. It checks that the namespace is
  absent, then INSERTs its properties, so a create racing another create
  of one namespace fails with `UncheckedSQLException` on the `exists`
  key, not `AlreadyExistsException`. It's a separate change: map the
  key's violation there to `AlreadyExistsException`, as #15434 did for
  tables.

## In fileio-catalog and catalog-bench

fileio-catalog's FileIOCatalog commits a namespace property change as a
record conditioned on the namespace's version, so a race is a conflict,
retried on a fresh read. catalog-bench's JDBC baseline runs on
`core-perf`, which has the fix since a603985e06. E7's JDBC runs from
before it count these failures as errors.
