|---|---|

## Summary

An expiry commits its removal, then refreshes the table and deletes the
files reachable only from the snapshots that its base (the metadata it
computed the removal on) has and the refreshed table lacks. It takes all
of them for its own. Another writer's removal is among them when:

- a REST server applies the expiry's `remove-snapshots` update to newer
  metadata. The commit carries no requirement on the table's snapshots or
  on main (an expiry that leaves specs and schemas alone sends
  `assert-table-uuid` alone), so the server applies it after any removal
  since the client's read;
- another removal lands between the expiry's commit and its cleanup's
  refresh, on any catalog.

The cleanup then deletes:

1. the files of snapshots another writer removed and kept the files of
   (`cleanExpiredFiles(false)`, `CleanupLevel.NONE`, or a cleanup it runs
   later, as Spark's action does): their manifest lists and manifests,
   and, cleaning by reachability, the data files only they reference;
2. cleaning incrementally, after another writer rolled main back and
   removed the snapshot it rolled back from (keeping its files), the data
   files that snapshot deleted, which are live in the table again.
   Incremental cleanup takes main's history from the base, where that
   snapshot is still main's, so the files it deleted look gone for good.

A catalog that swaps metadata (JDBC, Hive, Hadoop, `InMemoryCatalog`)
fails the commit when the table changed since the expiry's read, and the
expiry's retry computes its removal and cleans up on a fresh read: the
first window is REST's. The second is every catalog's.

## Reproduction

`TestExpiryCleanupStaleBase` (iceberg-core, package
`org.apache.iceberg.rest`, to come with the fix). The table: S1 appends
a, S2 appends b, S3 deletes b, its files in `InMemoryFileIO`. Writer Y's
expiry reads S1, S2 and S3 and removes S1, by id (reachable cleanup) or
as older than S2 (incremental cleanup: the table has only main). Writer X
either expires S2 with `cleanExpiredFiles(false)`, or rolls main back to
S2 and expires S3 with `cleanExpiredFiles(false)`. X runs on the REST
server (`RESTCatalogAdapter` over `InMemoryCatalog`, through Iceberg's
`CatalogHandlers`) just before it applies Y's update, or on
`InMemoryCatalog` just before or just after Y's commit:

| X's change, Y's cleanup | REST, before the server applies Y's removal | Swapping catalog, before Y's commit | Swapping catalog, after Y's commit |
|---|---|---|---|
| X expires S2, keeping its files; Y removes S1 by id | deletes S2's manifest list, its manifest, and b | keeps them | deletes them |
| the same; Y removes S1 by age | deletes S2's manifest list and manifest | keeps them | deletes them |
| X rolls main back to S2 and expires S3, keeping its files; Y removes S1 by age | deletes b, which S2, main's snapshot, reads | keeps b | deletes b |

Before Y's commit, the swapping catalog fails the commit and Y's retry
removes S1 from S1 and S3 (or S1 and S2), deleting S1's manifest list
alone. Alike on the `apache-iceberg-1.12.0` tag, on `main` at
`a6bc1f95e3` and on `core-fixes` (2026-11-18). After the third row, the
table's current snapshot lists b, and a read of it fails.

## Cause

`RemoveSnapshots.commit` cleans up with `cleanFiles(base, ops.refresh(),
level)`
([RemoveSnapshots.java#L360-L410](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/RemoveSnapshots.java#L360-L410)),
where `base` is the metadata the committed attempt computed its removal
on
([#L197](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/RemoveSnapshots.java#L197)).
Both strategies take the snapshots `base` has and the refreshed table
lacks for the expired ones
([ReachableFileCleanup.java#L67-L75](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/ReachableFileCleanup.java#L67-L75),
[IncrementalFileCleanup.java#L65-L77](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/IncrementalFileCleanup.java#L65-L77)).
Incremental cleanup takes main's history from `base`
([#L85-L96](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/IncrementalFileCleanup.java#L85-L96))
and deletes the files that expired snapshots of that history deleted
([#L223-L230](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/IncrementalFileCleanup.java#L223-L230),
[#L302](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/IncrementalFileCleanup.java#L302)),
whose own comment says it "must only remove files that were deleted in an
ancestor of the current table state to avoid physically deleting files
that were logically deleted in a commit that was rolled back". The
choice of strategy
([RemoveSnapshots.java#L394-L397](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/RemoveSnapshots.java#L394-L397),
#13614's) checks that every snapshot removed was on main in `base` and
that every snapshot left is on main now, not that main is where `base`
had it.

The difference is the expiry's own removal only if nothing else removed
a snapshot from `base` before the refresh. On a catalog that swaps
metadata the commit lands only on `base`, but the refresh comes after it.
On REST the commit need not land on `base`: `RESTTableOperations.commit`
sends the changes with `UpdateRequirements.forUpdateTable(base, updates)`
([RESTTableOperations.java#L211](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/rest/RESTTableOperations.java#L211)),
which derives requirements from ref, schema, spec and sort-order changes
and none from `RemoveSnapshots` (or, on 1.12.0, `RemoveSnapshotRef`)
([UpdateRequirements.java#L92-L116](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/UpdateRequirements.java#L92-L116)),
and `CatalogHandlers.updateTable` loads the table, checks the
requirements on it and applies the updates to it, loading it again and
applying them again on a conflict
([CatalogHandlers.java#L553](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/rest/CatalogHandlers.java#L553),
[#L617-L631](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/rest/CatalogHandlers.java#L617-L631)).

The server's half is the protocol as designed: "Requirements are
assertions that will be validated before attempting to make and commit
changes" (the REST spec's `updateTable`), and the spec's eight
requirements have none that pins a table's snapshots. The flaw is the
client's: its cleanup depends on more of `base` than its commit
asserted.

## Impact

- Files another writer kept are deleted. Spark's action commits its
  expiry with `CleanupLevel.NONE` and deletes what it computed afterwards
  (twice is harmless). A writer keeps files for good when they are not
  the table's to delete: data files shared with another table or added by
  `add_files`, the reason
  [#14287](https://github.com/apache/iceberg/pull/14287) gave for
  `CleanupLevel` (in 1.11.0). With `METADATA_ONLY` the remover deletes
  the manifests, so a racing expiry finds those data files only if it
  reads the manifests first.
- After a rollback whose snapshot another writer removed while keeping
  its files (Spark's action between its commit and its deletes, or
  `cleanExpiredFiles(false)`), an expiry by age that read the table
  before the rollback deletes data files live in the table, and reads of
  the current snapshot fail. Flink's table maintenance expires through
  `RemoveSnapshots` with its cleanup
  (`ExpireSnapshotsProcessor`, `CleanupLevel.ALL`), by age, so
  incrementally on a table with main alone. Rolling a bad commit back
  and expiring it with Spark's `expire_snapshots` (the action) is a common
  way to purge it.
- Both need the other writer's commits to land in a window of about one
  round trip: on REST from the expiry's read to the server's apply, with
  the server's own retries; on any catalog from the commit to the
  cleanup's refresh. Maintenance jobs racing each other, or a periodic
  expiry racing a manual rollback and expiry, are the cases.
- Spark's `ExpireSnapshotsSparkAction.expireFiles` reads `ops.current()`
  before its expiry and deletes the files of every snapshot that metadata
  has and the refresh after the commit lacks, less the files the
  refreshed table reaches
  ([spark/v4.1 ExpireSnapshotsSparkAction.java#L152-L184](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/spark/v4.1/spark/src/main/java/org/apache/iceberg/spark/actions/ExpireSnapshotsSparkAction.java#L152-L184),
  alike in v3.5 to v4.2). It deletes no live file, but it deletes others'
  kept files over a wider window: from the table's last refresh, before
  its expiry's own read, to after its commit, on every catalog. Read from
  the code, not reproduced.

## Fix

Clean up the snapshots this expiry removed, against what the table
reaches after it:

1. `RemoveSnapshots` keeps the snapshots its committed attempt removed
   (`base`'s, less those of the metadata it committed), and the cleanup
   expires those the refreshed table lacks, not every snapshot `base` has
   and the table lacks. What it keeps is still what the refreshed table
   reaches.
2. It cleans incrementally only when nothing else changed `base`'s
   snapshots: the snapshots `base` has and the refreshed table lacks are
   exactly the expiry's, and the refreshed table's main is `base`'s main
   or descends from it. Otherwise it cleans by reachability.
3. The strategies (`FileCleanupStrategy` and its two, package-private)
   take the expired snapshots instead of deriving them, statistics files
   included.
4. Spark's action, separately, deletes from the snapshots its expiry
   removed, which needs the core to report them (a method on
   `RemoveSnapshots` for its committed attempt's removal).

Without a race the cleanup is unchanged: `base` less the refreshed table
is the expiry's removal, and main has not moved. With one, the expiry
deletes what it would have, had the other writer's removal landed before
its read (its retry on a fresh read, where a catalog swaps metadata),
and leaves the other snapshots' files to the writer that removed them,
or to orphan-file removal.

The risk is small: the cleanup reads no more than reachable cleanup reads
now (the manifest lists of the snapshots it expires and of the refreshed
table's), and deletes only files of the snapshots it removed that the
refreshed table no longer reaches. The files of a racing writer's
snapshots are left to that writer, or to orphan-file removal: the leak
the fix accepts. Requirements can't do it: none
pins the snapshot set, `assert-ref-snapshot-id` on main (which would
fail the rollback case) would make every expiry conflict with every
commit to main, and the window after the commit is the client's on every
catalog.

## Tests

The reproduction above is the fix's test: its six failing cases must
pass with the fix, and its three passing ones (a swapping catalog raced
before the commit) must still pass.

## Before a PR

- **Not reported:** open an issue with the reproduction. Lead with the
  swapping catalog raced after the commit, which needs no REST; REST
  widens the window to the commit's round trip.
- **Incremental cleanup's future:** on #13568 amogh-jahagirdar (member)
  proposed deprecating incremental cleanup, "maybe 2.0", for reachable
  cleanup always. That removes the live-data case, not the kept-files
  one.
- **Other clients:** PyIceberg, iceberg-rust and iceberg-go send
  `remove-snapshots`; check whether any cleans up files after its expiry,
  and by what difference.
- **Spark's action** is a second change, needing the core to report its
  expiry's removal.

## In fileio-catalog

FileIOCatalog merged an expiry onto a changed table under
`fileio.catalog.expiry.merge` (errata D17 (expiry starves)'s fix), as a
REST server applies a removal, so its writer's cleanup, Iceberg's, ran on
a stale base: Bug 117 (merged expiry cleans stale base). Since 2026-11-17
(fileio 371a445) an expiry's read witness reads snapshot removal: it
conflicts with another removal since its read, and Iceberg's retry
cleans up from a fresh read. It merges past commits that add snapshots,
and never past a ref's reset, so the rollback case fails it too. The
window after the commit is Iceberg's on every catalog, FileIOCatalog's
included, and only the fix above closes it. Polaris 1.9.0 applies
`remove-snapshots` with `assert-table-uuid` alone to newer metadata
(catalog-bench's `c22-race.py`, in C22 (removal drops concurrent ref)),
so catalog-bench's expiries through Polaris meet the REST window.
