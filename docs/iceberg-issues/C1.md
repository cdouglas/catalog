# C1. A delete that merges manifests gives existing rows new ids

| | |
|---|---|
| **Affects** | Iceberg 1.10.1 and earlier v3 releases. |
| **Upstream** | **Fixed** by [#16263](https://github.com/apache/iceberg/pull/16263), "Core: Fix row ID assignment for EXISTING entry during a manifest merge" (commit `1cea23e`), released in **1.11.0**. |
| **Fix** | None in the fork. The fork has been on 1.12.0 since 2026-10-17, so nothing is left to upstream. |
| **Found by** | fileio-catalog's `TestCatalogFaultProperties`, whose row-lineage check found a data file's `first_row_id` changing. |

## Summary

On a v3 table, a delete whose commit also merges manifests gives an
existing data file a new `first_row_id`, so its rows' `_row_id`s change.
Without the merge, with a higher `commit.manifest.min-count-to-merge`, the
file keeps its ids.

## Reproduction (on 1.10.1)

```java
Table table =
    catalog.buildTable(ID, SCHEMA)
        .withProperty(TableProperties.FORMAT_VERSION, "3")
        .withProperty(TableProperties.MANIFEST_MIN_MERGE_COUNT, "2")
        .create();
table.newFastAppend().appendFile(file("f5")).commit();
table.newFastAppend().appendFile(file("f6")).commit();
table.rewriteManifests().clusterBy(file -> "all").commit();  // one manifest of f5 and f6
table.newFastAppend().appendFile(file("f8")).commit();
table.newFastAppend().appendFile(file("f10")).commit();
rowIds(table);                                      // f6 = 1

table.newDelete().deleteFile(path("f5")).commit();  // merges the three manifests
rowIds(table);                                      // f6 = 6
```

## Cause

The commit first filters the manifest that holds f5 and f6. That writes a
new manifest with f5 deleted, and f6 as an existing entry carrying its
inherited `first_row_id`. The new manifest has no manifest-level
`first_row_id` yet; the manifest list writer assigns one at the end of the
commit.

The same commit's merge then reads that uncommitted manifest. On a
manifest without a manifest-level `first_row_id`, `ManifestReader` cleared
every entry's `first_row_id`, including f6's explicit one. The merged
manifest then inherited a fresh range. #16263 makes the merge read
uncommitted manifests with an `isCommitted = false` reader, which keeps
explicit entry ids.

## Impact

Row lineage breaks for existing rows whenever a delete or overwrite also
merges manifests on a v3 table. With the default settings, merging starts
once a table has 100 manifests.

## In fileio-catalog

The workaround was `TestCatalogFaultProperties.V3_PROPERTIES`. It turned
off manifest merging on v3 tables, both on creation and on upgrade.
fileio-catalog
[`9296e10`](https://github.com/cdouglas/catalog/commit/9296e109cc950a567d9a52d08c5887f7f7e8c2e1),
the build onto 1.12.0, removed it, with the canary test
`aDeleteThatMergesManifestsRenumbersRows`. The fuzzer merges manifests on
v3 tables again, and its row-lineage check stays. Long runs on 1.12.0
(fault, 5,000 tries per property, several times) found no row-id change
from merges.

## Before a PR

Nothing to do: upstream fixed it. C2 is a related row-lineage bug that
#16263 did not fix: retries reuse stale manifest copies.
