## Summary

After another process drops a table, a handle's next refresh throws
NoSuchTableException. `BaseMetastoreTableOperations.refresh` then clears
the handle's metadata, its metadata location and its version, and, since
#1553, asks for another refresh on the handle's next use, so that the
use would fail the same way.

It doesn't. The metastores' `doRefresh` throws for a missing table only
if the operations have a current metadata location: without one, the
table is one not created yet, which is how a create finds its name free.
The first refresh cleared the location, so the second finds no table,
throws nothing, and leaves the handle no metadata: `current()` returns
null. Every update reads its base from `current()`, and fails with a
NullPointerException, not NoSuchTableException.

## Reproduction

```java
Table table = jdbcCatalog.loadTable(id);
jdbcCatalog.dropTable(id);

table.refresh();                                     // NoSuchTableException
table.refresh();                                     // returns, with no metadata
table.updateProperties().set("k", "v").commit();     // NullPointerException
```

The same with views, through `BaseViewOperations` and NoSuchViewException.
`TestIcebergCoreIssues.aHandleToADroppedTableKeepsFailingWithNoSuchTable`
runs it on table operations of its own that report a drop as Hive's and
JDBC's do (`InMemoryCatalog`'s don't); it fails on 1.12.0 and on `main` at
`97659351d4`.

## Cause

`BaseMetastoreTableOperations.refresh`
([BaseMetastoreTableOperations.java#L86-L101](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/BaseMetastoreTableOperations.java#L86-L101))
sets `currentMetadataLocation = null` when `doRefresh` throws.
`JdbcTableOperations.doRefresh`
([JdbcTableOperations.java#L84-L90](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/jdbc/JdbcTableOperations.java#L84-L90))
throws only if `currentMetadataLocation() != null`, and otherwise
disables refresh; `HiveTableOperations.doRefresh`
([HiveTableOperations.java#L191](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/hive-metastore/src/main/java/org/apache/iceberg/hive/HiveTableOperations.java#L191))
likewise, then refreshes from a null location
([#L205](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/hive-metastore/src/main/java/org/apache/iceberg/hive/HiveTableOperations.java#L205)).
`PropertiesUpdate.commit`
([PropertiesUpdate.java#L103](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/PropertiesUpdate.java#L103))
reads its retry settings from the null base; snapshot producers fail in
their constructors.

## Impact

A caller that handles a drop by catching NoSuchTableException, and uses
the handle again (to retry, or because something between swallowed the
first exception), gets a NullPointerException with no hint of the drop.
A commit with no base creates the table, as a create does; every update
reads its base first and fails before it gets there, but the handle's
state invites it.

## Fix

Remember that a refresh found the table gone, and fail every refresh
with NoSuchTableException until one finds the table again (it is
recreated, or registered again), asking for a refresh on every use in
between: a `doRefresh` that takes the table for a new one also disables
refresh. The state reset in the catch stays as it is, so a table
registered again at the same metadata location loads.

```java
try {
  doRefresh();
  if (dropped && currentMetadata == null) {
    throw new NoSuchTableException("Table does not exist: %s", tableName());
  }
} catch (NoSuchTableException e) {
  if (currentMetadataWasAvailable) {
    LOG.warn("Could not find the table during refresh, setting current metadata to null", e);
    dropped = true;
  }

  if (dropped) {
    // the next use refreshes again, and fails the same way until the table is back
    shouldRefresh = true;
  }
  ...
}
dropped = false;
```

`BaseViewOperations.refresh` gets the same, with NoSuchViewException.

## Tests

- `TestJdbcCatalog.testHandleToADroppedTableKeepsFailing`: after a drop,
  two refreshes, a properties update and an append on the handle each
  throw NoSuchTableException, and the table stays dropped.
- `TestJdbcViewCatalog.testHandleToADroppedViewKeepsFailing`: the same
  for a view.

Both fail without the fix: the second refresh returns. With it,
`TestJdbcCatalog`, `TestJdbcViewCatalog` and the full `iceberg-core`
test task pass.

## Before a PR

- **Cite #1513 and #1553**: this completes rdblue's design there, which
  the cleared location defeats.
- **Alternative:** keep the location in the catch, so `doRefresh` keeps
  throwing. One line, but a table registered again at the same metadata
  location would then not load (`refreshFromMetadataLocation` skips a
  location it already has), and it changes what `currentMetadataLocation()`
  returns after a drop.
- **Run the Hive and Glue tests**, whose operations take this path; the
  fix is in the base classes, so no catalog changes.

## In fileio-catalog

`LogCatalog`'s table operations tell a dropped table from a new one by
whether a read has found it (Bug 78), so it works on stock Iceberg too;
the canary checks the base classes, with operations of its own.
