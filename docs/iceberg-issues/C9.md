## Summary

A create-or-replace transaction (`createOrReplaceTransaction`) that begins
when its table does not exist builds the table as a new one, with a fresh
UUID. Suppose another writer creates the table before the transaction
commits. Then what happens depends on when the create lands:

- before the commit refreshes the table: the commit puts the new table it
  built over the one the other writer created. The table takes the
  transaction's UUID, and loses the created table's history.
- after the refresh: the commit is a create, and fails with
  `AlreadyExistsException`. A REST catalog fails it this way in either
  case.

Neither order of the two commits gives the first outcome. Run after the
create, a create-or-replace replaces the table and keeps its UUID and
history (`TableMetadata.buildReplacement`). Run before it, the create
would have failed, and it did not.

## Reproduction

```java
Transaction createOrReplace = catalog.buildTable(ID, SCHEMA).createOrReplaceTransaction();
createOrReplace.newFastAppend().appendFile(file("a")).commit();

Table created = catalog.createTable(ID, SCHEMA);          // another writer
created.newFastAppend().appendFile(file("b")).commit();
long appended = created.currentSnapshot().snapshotId();

createOrReplace.commitTransaction();                       // succeeds

Table table = catalog.loadTable(ID);
table.uuid();               // the transaction's UUID, not created.uuid()
table.snapshot(appended);   // null: the created table's history is gone
```

## Cause

`BaseTransaction.commitReplaceTransaction` refreshes the table on each
attempt. A table that does not exist is fine for a create-or-replace
([BaseTransaction.java#L314-L320](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/BaseTransaction.java#L314-L320)).
It then commits the metadata it built at the start over whatever the
refresh found
([#L322-L328](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/BaseTransaction.java#L322-L328)).
That metadata came from `TableMetadata.newTableMetadata` when the table
did not exist, so it is a different table: its own UUID, no snapshots, no
schema or spec history. Nothing checks that the refreshed table is the one
the metadata was built for. A handle does check that, but a handle with no
table has nothing to compare: `BaseMetastoreTableOperations` fails a
refresh to a table with another UUID ("Table UUID does not match",
[BaseMetastoreTableOperations.java#L206](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/BaseMetastoreTableOperations.java#L206)),
and has no metadata here.

`CatalogTests.testCreateOrReplaceTransactionConcurrentCreate`
([CatalogTests.java#L2695-L2734](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/test/java/org/apache/iceberg/catalog/CatalogTests.java#L2695-L2734))
runs this race and expects `AlreadyExistsException` and the created table
unchanged. It is skipped unless the catalog reports server-side retries,
"Conversion to replace transaction is not supported by REST catalog", so
it has never run on a metastore catalog.

## Impact

A `CREATE OR REPLACE TABLE` that races a `CREATE TABLE` of the same table
on a metastore catalog can succeed and leave a different table under the
name:

- Handles to the created table, and readers that pinned its UUID, find a
  table with another UUID and fail ("Table UUID does not match").
- Snapshots the other writer committed to the new table drop out of its
  history. That writer was told its commits succeeded; their data files
  are no longer referenced, so expiry never deletes them.

In other interleavings the same race fails with `AlreadyExistsException`, so
the outcome depends on timing.

## Fix

When the transaction began without its table and the refresh finds one,
fail as a create does:

```java
// without a table when it began, the transaction built its replacement as a new table
boolean replacesNoTable = base == null;
...
if (replacesNoTable && underlyingOps.current() != null) {
  throw new AlreadyExistsException("Table already exists: %s", tableName);
}
```

`AlreadyExistsException` is not retried, and the transaction's files are
cleaned up as for any failed replace. The create-or-replace now fails in
every interleaving, as the REST catalog fails it and as the existing
`CatalogTests` case expects. The fix removes that case's assumption, so it
runs for every catalog.

## Tests

- `TestReplaceTransaction.testCreateOrReplaceTransactionWithConcurrentCreate`,
  on every format version: the reproduction above. It checks that the
  commit fails with `AlreadyExistsException`, and that the created table
  keeps its UUID and its snapshot. All 4 cases fail on 1.12.0.
- `CatalogTests.testCreateOrReplaceTransactionConcurrentCreate`, now for
  every catalog. On 1.12.0 it fails for the in-memory and JDBC catalogs and
  passes for REST.

With the fix, the full `iceberg-core` check passes, `CatalogTests`
included for the in-memory, JDBC and REST catalogs. fileio-catalog's
`TestLocalCatalog` runs the `CatalogTests` case in each of its nine modes.

## Before a PR

- **Coordinate with #16943.** When the table changed, that PR rebuilds the
  replacement on the refreshed table and replays the transaction's
  updates. That includes this case, where the table appeared. Where the
  rebuild works, a create-or-replace would replace the created table and
  keep its UUID and history. Where the rebuilt schema, spec, sort order or
  format version would differ, it commits the metadata as built, which is
  this bug. So the two fixes give different results where both apply:
  - this fix fails the race;
  - #16943 turns it into a replace.

  The tests disagree too. #16943 would need
  `testCreateOrReplaceTransactionConcurrentCreate` to stay skipped for
  metastore catalogs, or to expect a replace there.

  Options:
  - this fix alone: the race fails, as on REST;
  - with #16943, apply this check only where #16943 falls back;
  - a comment on #16943 with this reproduction, asking which it intends.
- **Framing.** A reviewer may read this fix as [#16289](https://github.com/apache/iceberg/pull/16289)'s, which failed
  a replace of a table that existed on any concurrent change. rdblue
  (member) gave that a -1: "The contract of REPLACE TABLE is that the
  table's data, schema, and partitioning are replaced. There are no
  assumptions to validate". The race here is different: the transaction
  began without a table, so it built a new one and has no history to keep;
  it fails as a create does. For a table that existed, he backs a rebuild
  like #16943's. On dev@ ("[DISCUSS] Allow Commit Conflicts in
  REPLACE TABLE transactions", 2025-08-06): "The transaction should retry
  and update the latest metadata.json rather than blindly replacing it."
- **The test's assumption.** The skip message, "Conversion to replace
  transaction is not supported by REST catalog", suggests the conversion
  on metastore catalogs was meant. If so, the review should settle whether
  that conversion is a feature to fix (#16943's rebuild) or a behavior to
  drop (this fix).
- **Other catalogs' tests.** Removing the assumption runs the case for the
  Hive, Nessie and BigQuery `CatalogTests` suites too. All three are
  metastore catalogs, which go through the same code, so they should pass,
  but only the core suites were run here.

## In fileio-catalog

There was no workaround: the fuzzer expected the outcome of a serial run,
and found the bug. Its `REPLACE_TABLE` model already counts the
`AlreadyExistsException` of this race as a rejection (accepted behavior A2
in `docs/ICEBERG_ISSUES.md`), which now covers both interleavings. The
canary is
`TestIcebergCoreIssues.aCreateOrReplaceKeepsATableCreatedSinceItBegan`.
It asserts only that the created table keeps its UUID and history, so a
fix that replaces it properly passes too.
