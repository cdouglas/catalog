# C32. A partitions-table row depends on the order its manifests are read

| | |
|---|---|
| **Affects** | Iceberg 1.12.0, and `main` at `a6bc1f95e3` (2026-11-16): `PartitionsTable.Partition.update`, which takes a partition's `spec_id`, `last_updated_at` and `last_updated_snapshot_id` from the first file it reads of the partition's newest snapshot, over manifests that `PartitionsTable.planEntries` reads in parallel on the scan's plan executor (Iceberg's worker pool by default). |
| **Upstream** | Not reported. When `spec_id` was added (PR [#4516](https://github.com/apache/iceberg/pull/4516), 2022), szehon-ho (member) asked in review whether files of one partition under two specs would "show up with a random one", and whether the spec id belonged in the key; the follow-up, [#4560](https://github.com/apache/iceberg/pull/4560), merged such files into one row, and [#7581](https://github.com/apache/iceberg/pull/7581) (2023) made the columns follow the newest snapshot, leaving a tie to the read order. Searched apache/iceberg's issues, PRs and PR branches and the issues@ and dev@ lists (copies of 2026-10-21) and GitHub's search (2026-11-18). |
| **Fix** | `core-fixes` [`c82e05c`](https://github.com/cdouglas/iceberg/commit/c82e05cd72a0f7b822cd43fdd5542620b2ff995e), "Core: Pick a partition's last update alike in any read order" (below). |
| **Found by** | fileio-catalog's differential fuzzer (`TestInlineDifferentialProperties`), round p12-r0p, 2026-11-17: PARTITIONS `spec_id` 0 against 1 for one partition, between a pointer catalog's and an inline catalog's copies of one table, and between the inline table and its own serialized copy, whose metadata is the same. |

## Summary

The PARTITIONS metadata table has one row per partition of the table's
unified partition type (`Partitioning.partitionType`), so files written
under different specs are one row where their partition values coincide.
The row's `spec_id`, `last_updated_at` and `last_updated_snapshot_id`
come from one file: the first the scan reads among those of the
partition's newest snapshot. The scan reads the snapshot's manifests in
parallel, so which file is first depends on the threads. Where one
snapshot adds files of one partition under two specs, two scans of one
table can report different `spec_id`s; where two snapshots that touch a
partition share a commit time to the millisecond, different
`last_updated_snapshot_id`s too. The counts are sums, and agree.

## Reproduction

A v2 table partitioned by `identity(cat)` (spec 0), then with the field
renamed (spec 1: the same field id and transform, so one partition of
the unified type), and one row delta that adds a data file of spec 0 and
a position delete file of spec 1, both in `cat=null`. The snapshot has
two manifests. Read on a direct executor (manifest-list order), the row
says `spec_id=0`; read on an executor that runs the two manifests' reads
in reverse, `spec_id=1`. fileio-catalog's `TestMetadataTableOrder` builds
this table; the canary below reads it both ways.

## Cause

`Partition.update` replaces the row's spec and last update only for a
file of a strictly newer commit time:

```java
long snapshotCommitTime = snapshot.timestampMillis() * 1000;
if (this.lastUpdatedAt == null || snapshotCommitTime > this.lastUpdatedAt) {
  this.specId = file.specId();
  ...
```

so on a tie the first file read wins, and `planEntries` returns the
entries through a `ParallelIterable` over the manifests, on
`scan.planExecutor()`.

## Impact

Low: a reporting column of a metadata table, and only after partition
evolution that leaves some partition tuples unchanged (a renamed field,
or a dropped one whose old files held null there), with a commit that
then writes one partition under both specs. Merge-on-read does that: new
rows go to the current spec and delete files to the spec of the data
files they delete from. The cost is non-reproducible metadata queries:
`SELECT spec_id FROM t.partitions` can change between two runs on one
table state, which breaks tests and differential checks, and anything
that keys on the column.

## Fix

`core-fixes` c82e05c breaks a tie of commit times on the snapshot's
sequence number, then its id, then the file's spec id, taking the
greatest: any order of the same files gives the same row. For one
snapshot's files of a partition that is the newest spec among them;
between snapshots of one millisecond, the later by sequence number
(by id on v1, whose sequence numbers are all 0). Without a tie nothing
changes. The partition keeps the sequence number of its last update, and
gains package-private accessors for its spec id and last update, for the
test.

## Tests

`TestMetadataTableScans.partitionsTableIsTheSameInAnyManifestOrder`
(iceberg-core; every format version): one fast append of a file of
spec 0 and one of spec 1 (a rename of spec 0's field) in one partition,
read in manifest-list order and in reverse. It fails on 1.12.0 and passes
with the fix. fileio-catalog's canary, `TestIcebergCoreIssues
.aPartitionsRowIsTheSameInAnyManifestOrder`, reads the row-delta table
above both ways on `InMemoryCatalog`.

## Before a PR

- **Not reported:** a PR with the test may do; cite #4516's review
  question, which it answers.
- **Which spec to report:** the greatest spec id is a choice. A reviewer
  may prefer a data file's spec over a delete file's; any rule that does
  not depend on the order is a fix.
- **Other readers:** Trino and PyIceberg compute their partitions tables
  themselves; check their tie-breaks.

## In fileio-catalog

The differential oracle compares every metadata table of the pointer and
inline copies of a table (`TableViews`). Since fileio 83513ce it plans
metadata tables on a direct executor, in manifest-list order, so it
compares the same reading of each; with the fix, PARTITIONS reads alike
in any order as well. `TestMetadataTableOrder` checks the oracle's view of
the table above.
