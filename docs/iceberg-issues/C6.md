# C6. A repeated cherry-pick leaves a table it can't plan

| | |
|---|---|
| **Affects** | Iceberg 1.10.1 and 1.12.0, and `main` at `524fe9e` (2026-10-16). The files the fix changes have not changed on `main` between `524fe9e` and `9bbee07` (2026-10-18). |
| **Upstream** | Not reported (searched apache/iceberg issues and PRs, 2026-10-16). |
| **Fix** | [`724608a`](https://github.com/cdouglas/iceberg/commit/724608a099eec717e59b11cd09cb062a4dfceb28) on [`core-fixes`](https://github.com/cdouglas/iceberg/tree/core-fixes), "Core: Refuse a cherry-pick repeated after its earlier pick expired". 2 files, +123. Cherry-picks cleanly onto `main` at `9bbee07`. |
| **Found by** | fileio-catalog's `TestInlineDifferentialProperties`: planning `main` failed in both catalogs alike. |

## Summary

Cherry-picking a snapshot normally fails if it was already picked: "already
picked to create ancestor", or for write-audit-publish, "Duplicate request
to cherry pick wap id". Once an expiry has removed the snapshot made by the
earlier pick, the duplicate goes through. The picked snapshot's data files
are added a second time, at a new data sequence number.

The table now lists the same data file twice, so its rows are duplicated.
Once one of those files has a deletion vector, planning `main` fails:

```
DV data sequence number (5) must be greater than or equal to data file sequence number (7)
```

## Reproduction

```java
Table table =
    catalog.buildTable(ID, SCHEMA).withProperty(TableProperties.FORMAT_VERSION, "3").create();
table.newFastAppend().appendFile(file("x")).commit();
DataFile staged = file("d");
table.newFastAppend().appendFile(staged).stageOnly().commit();
long stagedId = Iterables.getLast(table.snapshots()).snapshotId();
table.newFastAppend().appendFile(file("y")).commit();
table.manageSnapshots().cherrypick(stagedId).commit();
long picked = table.currentSnapshot().snapshotId();
table.newRowDelta().addDeletes(dv(table, staged)).commit();  // a deletion vector for d
table.newFastAppend().appendFile(file("z")).commit();
table.manageSnapshots().cherrypick(stagedId).commit();  // refused: "already picked"

table.expireSnapshots().expireSnapshotId(picked).commit();
table.manageSnapshots().cherrypick(stagedId).commit();  // accepted: d is added again

table.newScan().planFiles();  // ValidationException: DV data sequence number ...
```

## Cause

`CherryPickOperation.validate`
([CherryPickOperation.java#L162](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/CherryPickOperation.java#L162))
looks for an earlier pick in the history only, among the current
snapshot's ancestors:

- `validateNonAncestor`
  ([#L207](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/CherryPickOperation.java#L207))
  and `lookupAncestorBySourceSnapshot`
  ([#L268](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/CherryPickOperation.java#L268))
  look for an ancestor whose summary has the picked snapshot as its
  `source-snapshot-id`;
- `WapUtil.isWapIdPublished`
  ([WapUtil.java#L60](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/util/WapUtil.java#L60))
  looks for an ancestor that published the same `wap.id`.

Snapshot expiry removes ancestors. Once the ancestor that recorded the
pick is gone, both checks pass.

## Impact

- **Duplicate rows:** the second pick adds the same data files again.
- **Unplannable table:** in v3, a table whose re-added file has a deletion
  vector can't be planned at all.

A likely way to hit it is a write-audit-publish job that publishes again,
say on a retry, after a snapshot expiry has run.

## Fix

When the history may be missing an earlier pick, the pick checks the
table's contents instead: it refuses if any data file it would add is
already live in the current snapshot.

```
Cannot cherry-pick snapshot <id>: data file <path> is already in the table
```

**When the history may be missing an earlier pick:** an earlier pick
always has a higher sequence number than the picked snapshot. Expired
ancestors have lower sequence numbers than the oldest ancestor that
remains. So an expiry can only have removed an earlier pick when both of
these hold:

- the current snapshot's ancestry is cut short: the oldest remaining
  ancestor has a parent id the table no longer has;
- that oldest ancestor's sequence number is higher than the picked
  snapshot's.

v1 tables have no sequence numbers, so on v1 the check runs whenever the
ancestry is cut short. On v2 and later, a table whose expired history is
older than the picked snapshot pays nothing.

The check reads the current snapshot's data manifests, projecting only
`file_path`. It runs only for append and dynamic-overwrite picks, the ones
that add files; fast-forwards don't.

## Tests

In `TestWapWorkflow`, on every format version:

- `testCherrypickAgainAfterItsPickExpired`: a pick repeated after an
  expiry removed the earlier pick. Refused; the table's files are
  unchanged.
- `testWapPublishAgainAfterItsPublishExpired`: the same for a `wap.id`
  publish.
- `testCherrypickAfterAnExpiry`: a pick after an expiry that removed only
  older history. Accepted.

The first two fail on 1.12.0 (8 cases). With the fix,
`TestWapWorkflow`, `TestSnapshotManager`, `TestRowLineageAssignment` and
the full `iceberg-core` check pass.

## Before a PR

This is the least certain of the fixes to be accepted upstream. Points to
raise or decide:

- **Cost:** the content check reads every data manifest of the current
  snapshot (`file_path` only). It runs only when an expiry may have
  removed an earlier pick, which on v2+ means the expired history is newer
  than the picked snapshot. A cheaper check could read only the manifests
  whose `added_snapshot_id` is a snapshot no longer in the table, since an
  earlier pick's files are added by its snapshot. But later merges rewrite
  manifests, so that is less certain to find them.
- **Semantics:** the check refuses any pick whose files are already live,
  even when they got there some other way, such as an independent append
  of the same path. Adding them again would duplicate them anyway.
- **Exception type:** it throws a plain `ValidationException`. A
  `CherrypickAncestorCommitException` would need an ancestor id, which is
  gone. `DuplicateWAPCommitException` would fit the `wap.id` case only.
- **Alternatives:**
  - only document the limitation in the `cherrypick` Javadoc;
  - have expiry keep, in the table metadata, a record of the
    `source-snapshot-id` and published `wap.id`s of the snapshots it
    removes. That is a much larger change.

## In fileio-catalog

The workaround was in `TestInlineDifferentialProperties.files`: it
compared a planning failure as the string "fails: ...", which both
catalogs had to produce alike.
[`e2c6b7b`](https://github.com/cdouglas/catalog/commit/e2c6b7b8a13c7d07df988a12d113c25dec48b9ef)
removed it, with the canary test. Removing it means a planning failure
fails the property. With the workaround removed and without the fix, the
differential fuzzer did not reproduce C6 in 3,000 tries, so its coverage
of this case is weak. The core tests above and a new canary,
`TestIcebergCoreIssues.aCherryPickRepeatedAfterAnExpiryIsRefused`, which
asserts the bug is absent, are the evidence.
