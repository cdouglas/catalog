# C34. A JDBC namespace create that loses to a concurrent create fails with UncheckedSQLException

| | |
|---|---|
| **Affects** | Iceberg 1.12.0, and `main` at `3ad26de2bd` (2026-11-02): `JdbcCatalog.createNamespace`, which checks that the namespace is absent, then INSERTs its properties as a separate statement. |
| **Upstream** | Reported: [#18759](https://github.com/apache/iceberg/issues/18759) (2026-11-02, open), with the REST fixture returning 500s to 7-31 of 120 concurrent creates of one namespace, on SQLite and on Postgres (Gravitino). Fix in PR [#18760](https://github.com/apache/iceberg/pull/18760) (open; approved by ebyhr, member, 2026-11-04), which the fork takes and narrows (below). iceberg-go fixed the same race in its SQL catalog the same way ([apache/iceberg-go#1635](https://github.com/apache/iceberg-go/pull/1635)). |
| **Fix** | `core-fixes` [`584bcfd`](https://github.com/cdouglas/iceberg/commit/584bcfd97b), "Core: Report a JDBC namespace create that loses to a concurrent one as existing" (below). |
| **Found by** | Reading `createNamespace` while recording C33 (JDBC property set races), 2026-11-19: it has the same check-then-insert shape. |

## Summary

Two creates of one namespace that both find it absent both INSERT its
properties. The INSERT that runs second fails on the table's primary key
(catalog, namespace, key), on the `exists` row at least. That failure
comes out as `UncheckedSQLException`, which a REST server returns as a
500. A create that runs its check after the winner's INSERT gets
`AlreadyExistsException` (409).

Nothing is damaged: there's exactly one winner, and the loser's INSERT, a
single statement, writes none of its properties. The fault is the
report: a 500 tells the client its create may or may not have happened,
when the catalog knows it didn't.

## Reproduction

Two `JdbcCatalog`s on one SQLite database. The first's connections let the
second create the namespace just before the first's INSERT of its
properties, after its check found the namespace absent. The first's
create then fails with `UncheckedSQLException: Failed to execute: INSERT
INTO iceberg_namespace_properties ...`. `TestJdbcCatalog
.testCreateNamespaceRacingACreateOfIt` and fileio-catalog's canary do
this. #18760's test does the same with a Mockito spy whose first
`namespaceExists` returns false.

## Cause

```java
if (namespaceExists(namespace)) {
  throw new AlreadyExistsException("Namespace already exists: %s", namespace);
}
...
insertProperties(namespace, createMetadata); // no handling of the key's violation
```

## Fix

`core-fixes` 584bcfd takes #18760: when the INSERT fails, the create
checks again whether the namespace exists, and throws
`AlreadyExistsException` if it does. The fork narrows the second check
to an INSERT that failed on the key (`JdbcUtil.isConstraintViolation`,
which `JdbcTableOperations` already uses for a create's INSERT).

The narrowing matters because of `JdbcClientPool`. When the connection
is lost after the INSERT committed, the pool runs the INSERT again. The
second run meets the row the first inserted, and the pool reports the
lost connection, not the key. Under #18760 alone, the second check would
find the namespace, which this create made, and report it as another's.
With the narrowing, that create's failure stays an
`UncheckedSQLException`, whose outcome is unknown, as it was. C28 (JDBC
unclear commit) handles the same lost reply for a table's create, by its
metadata file. A namespace has no such token to tell its creator by.

## Tests

`TestJdbcCatalog` (iceberg-core):

- `testCreateNamespaceLosingConcurrentCreate`: #18760's test. It fails
  on 1.12.0.
- `testCreateNamespaceRacingACreateOfIt`: another writer's create on one
  SQLite database between the check and the INSERT. It fails on 1.12.0.
- `testCreateNamespaceWhoseInsertReplyIsLostIsNotReportedAsAnothers`:
  C28's fault pool loses the INSERT's reply. It fails with #18760 alone,
  which reports `AlreadyExistsException`.

fileio-catalog's canary is `TestIcebergCoreIssues
.aJdbcNamespaceCreateLosingARaceReportsItExists`.

## Before a PR

- **Don't file:** #18759 reports it and #18760 fixes it, approved. Offer
  the narrowing there, with the lost-reply test, as a review comment or a
  follow-up. That test needs a fault-injecting client pool, which
  upstream's `TestJdbcCatalog` doesn't have.
- **Cherry-picking:** the main change applies to `main` on its own. The
  race and lost-reply tests use the helpers of C33's and C28's commits.

## In fileio-catalog

Nothing to work around. FileIOCatalog's namespace create binds the name
by the record's conditions, so a create that loses its race retries on a
fresh read, which finds the namespace and reports
`AlreadyExistsException`.
