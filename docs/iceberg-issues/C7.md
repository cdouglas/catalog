# C7. The all_* metadata tables miss the row ids of an upgraded file

| | |
|---|---|
| **Affects** | Iceberg 1.10.1 and 1.12.0, and `main` at `524fe9e` (2026-10-16). The files the fix changes have not changed on `main` between `524fe9e` and `9bbee07` (2026-10-18). |
| **Upstream** | Not reported (searched apache/iceberg issues and PRs, 2026-10-16). |
| **Fix** | [`2779515`](https://github.com/cdouglas/iceberg/commit/27795151cf7ec998a6ee018e31f6cbe85b021cd1) on [`core-fixes`](https://github.com/cdouglas/iceberg/tree/core-fixes), "Core: Keep the row ids of upgraded manifests in all_* metadata tables". 2 files, +69/−2. Cherry-picks cleanly onto `main` at `9bbee07`. |
| **Found by** | fileio-catalog's `TestInlineDifferentialProperties`, which compares every metadata table between two catalogs that ran the same operations. The two disagreed on `first_row_id` from one run to the next. |

## Summary

The `all_*` metadata tables (`all_data_files`, `all_files`,
`all_delete_files`, `all_entries`) can report no `first_row_id` for a data
file that has row ids. The file must be in a manifest carried across an
upgrade to v3. Which answer a query gets depends on thread timing.

## Reproduction

```java
Table table = catalog.createTable(ID, SCHEMA);                // v2
table.newFastAppend().appendFile(file("f0")).commit();
table.updateProperties().set(TableProperties.FORMAT_VERSION, "3").commit();
table.newFastAppend().appendFile(file("f1")).commit();       // assigns f0's manifest row ids

firstRowIds(table, MetadataTableType.FILES);           // {f0=1, f1=0}
firstRowIds(table, MetadataTableType.ALL_DATA_FILES);  // {f0=null, f1=0}, usually
```

## Cause

`BaseAllMetadataTableScan.reachableManifests` reads the manifest list of
every snapshot in a `ParallelIterable`, and dedupes the manifests with a
`HashSet`
([BaseAllMetadataTableScan.java#L74-L86](https://github.com/apache/iceberg/blob/apache-iceberg-1.12.0/core/src/main/java/org/apache/iceberg/BaseAllMetadataTableScan.java#L74-L86)).
`GenericManifestFile.equals` compares paths only, so the set keeps
whichever copy of a manifest it reads first.

A manifest carried across a v3 upgrade has two kinds of copies:

- in the lists written before the upgrade, `first_row_id` is null;
- in the first list after it and later ones, the manifest has an assigned
  `first_row_id`.

The scan then reads the manifest with whichever copy won. A data file in
it inherits its row ids from that copy's `first_row_id`, or gets none.

## Impact

Wrong `first_row_id` values in the `all_*` tables of v3 tables upgraded
from v2. The values also vary between runs. Snapshot-scoped tables
(`files`, `entries`) and scans are not affected; they read one manifest
list.

## Fix

Dedupe by path into a map, merging copies so that one with an assigned
`first_row_id` wins over one without. If two copies have different ids
(only possible with C2), the smaller wins, so the result doesn't depend on
read order:

```java
Map<String, ManifestFile> manifestsByPath = Maps.newHashMap();
for (ManifestFile manifest : iterable) {
  manifestsByPath.merge(
      manifest.path(), manifest, BaseAllMetadataTableScan::withAssignedFirstRowId);
}
```

## Tests

`TestRowLineageAssignment.testAllDataFilesAfterUpgrade`. It upgrades a
table whose snapshots carry manifests from v2, and assigns row ids with an
empty commit. Then it checks that `all_data_files` reports, for each file
in a carried manifest, the row id that `data_files` reports. It also
checks that a manifest no snapshot since the upgrade has keeps null ids.

The test plans the metadata table on a direct executor. With one thread,
`ParallelIterable` reads the lists oldest first, so the test fails on
1.12.0 every time. With the worker pool, the order varies; in one run the
test passed by chance.

## Before a PR

- **A design choice to flag:** the test leans on `planWith(direct
  executor)` to fix the read order. A reviewer may prefer a test that
  builds the duplicate copies directly.
- **Merge order:** the C2 commit, which sits on this one, adds its tests
  next to this one's in the same class. A cherry-pick of C2 onto `main`
  without this commit conflicts in that test file; the fix is trivial.

## In fileio-catalog

The workaround was a mask of `first_row_id` in the `all_*` tables, in
`TestInlineDifferentialProperties.metadataTable`.
[`b82ceb9`](https://github.com/cdouglas/catalog/commit/b82ceb9cbd967f2f2687d38920c5ddc5dc73ff9a)
removed it, with the canary test. With the mask removed and without the
fix, the differential fuzzer finds C7 within 20 tries. A new canary,
`TestIcebergCoreIssues.allDataFilesHasTheRowIdsOfAFileCarriedAcrossAnUpgrade`,
asserts the bug is absent.
