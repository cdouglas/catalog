# Catalog File Explorer

A self-contained HTML page that shows catalog files (`AtomicFileLog`'s layout,
[ATOMIC_FILE_LOG.md](../ATOMIC_FILE_LOG.md)) byte by byte: the header, the checkpoint and each
record, in a Wireshark-style three-pane layout (hex, decoded tree, field detail). It decodes with
the format's schemas of record, intentlog-core's `log.proto` for the envelope of the checkpoint and
each record, and the catalog module's `catalog.proto` for the catalog's messages inside them, which
are embedded in the page as one schema with a set of scenarios. The scenarios are generated from the
codecs (`FormatExplorerFixtures`), and `TestFormatExplorer` fails the build when the embedded copy
is stale, so the page always shows what the implementation writes.

## Open the explorer

Open `index.html` in any modern browser via `file://`. No server is needed; the schema, the
scenarios, the decoder and the UI are all in the page.

Click any byte in the hex pane or any node in the tree to see the field's name, number, wire
type, declared type and `.proto` comment, and its decoded value. Enum values decode to their
names, and the 16-byte UUIDs and the compressed committed-transaction set to UUID strings.

## Load a catalog file

Click **"📂 Load catalog file…"** or drop a file anywhere on the page. The tree and hex panes
decode it as they do a scenario, which helps when triaging a corrupt or unfamiliar file. To get
the files a test suite writes, run it with `-Dexplorer.dump=<dir>` (see [Check the
decoder](#check-the-decoder)).

Inline table metadata (`InlineTable.metadata`, `CreateTableInline.metadata`,
`UpdateTableInline.full_metadata`) is decoded in the browser with `DecompressionStream('gzip')`:

- **`CODEC_JSON_GZIP`**: gunzip, then the TableMetadata JSON, pretty-printed.
- **`CODEC_STRUCTURAL`**: gunzip, then the layout's top level: its version
  (`StructuralInlineMetadataCodec.FORMAT_VERSION`, which the page knows from its fixtures), the
  JSON without snapshots and metadata log, and the `snap_block` and `mdlog_block`, whose bytes the
  compact form lists. Snapshots are not rebuilt in the page; for that, use the Java codec
  (`StructuralInlineMetadataCodec.decodeFull`).

`AddSchema.schema_json` and `AddPartitionSpec.spec_json` are gzip-compressed JSON and get the
same two expanders: **Show recovered JSON** and **Show compact form**. The decode runs
asynchronously; a node clicked before it finishes shows a placeholder until the detail pane
re-renders.

## What it flags

Nodes marked ⚠ (red) are explained in the detail pane:

- **QUIRK**: a negative int32 (a late-bound id, a `-1` version) is a 5-byte varint, not
  proto3's 10-byte sign extension. `ProtoCodec.writeRawVarint(int)` shifts a 32-bit int right
  unsigned; readers generated by `protoc` accept the short form.
- **SCHEMA DRIFT**: bytes that depart from catalog.proto. These are a field the schema lacks, a
  wire type its declared type does not allow, an enum value it does not declare, or a repeated
  number written packed where the schema says `[packed = false]`. In a file the current code
  wrote, drift means catalog.proto or the codec is wrong. In an older file it means the format
  changed since.

## Bundled scenarios

| # | Name | Teaches |
|---|------|---------|
| 1 | `empty-bootstrap` | header, framing, the root namespace row, the Action oneof, a late-bound create |
| 2 | `txn-multi-action-with-late-bind` | a create naming a namespace created in the same transaction; 5-byte negative varints |
| 3 | `create-table-inline-gzip` | inline metadata in `CODEC_JSON_GZIP`; a CAS write (checkpoint + the commit's record) |
| 4 | `create-table-inline-structural` | inline metadata in `CODEC_STRUCTURAL`, segment by segment |
| 5 | `update-table-inline-delta` | an append as a `TableMetadataDelta`: fixed64, zigzag sint64, the deepest nesting |
| 6 | `evolve-table-inline-delta` | schema, partition spec, sort order and property updates in one delta |
| 7 | `pointer-multi-table-conflict-retry` | atomic multi-table commits, version-based conflicts, a rejected record left in the log |
| 8 | `inline-multi-table-conflict-retry` | the same with inline tables and deltas |
| 9 | `concurrent-creates-bound-at-replay` | three writers of one snapshot: replay binds their ids in log order; the parent's version serializes creates under it |
| 10 | `rename-table-across-namespaces` | `RenameTable` (Action 11), and a stale update it rejects |
| 11 | `inline-manifest-list` | an inline-ML table: the manifest pool, per-snapshot indices, `AddManifestDelta.position` |
| 12 | `compaction-with-committed-set-gc` | the committed-transaction set, its GC horizon and the unknown answer below it |

Each record's note says what it does and how replay treats it. Notes on the whole file appear
under the scenario's description.

## Regenerate the fixtures

`FormatExplorerFixtures` builds each scenario the way a writer builds a catalog file. Each record
holds the intention `CatalogMutation.intention` makes for a change to the snapshot its
writer read, a CAS write is a checkpoint of the base followed by the commit's record, and an
inline delta is the one `InlineDeltaCodec.computeDelta` sends (inline-ML manifest updates are
written by hand). Transaction ids, table UUIDs and times are pinned, so the bytes are stable.
Generation fails unless each file conforms to catalog.proto and replays to the outcome its notes
describe.

```bash
# From fileio-catalog/: regenerate, writing index.html in place
mvn test -Dtest=FormatExplorerFixtures -Dexplorer.regenerate=true
```

The generator also writes `target/format-explorer/fixtures.json`. Regenerate after any change to
catalog.proto, `ProtoCodec`, `InlineDeltaCodec`, the inline metadata codecs or the writer's
action building; `TestFormatExplorer.fixturesAreCurrent` fails until you do.

`TestFormatExplorer` runs with every `mvn test`. It checks that:

- each codec field-number constant numbers a field catalog.proto declares, under a name that says
  the same, and each declared field has a constant;
- the embedded fixtures equal the generated ones. Gzip output depends on the JDK's zlib build, so
  this check runs only where the fixtures' `deflateProbe` matches, and is skipped elsewhere;
- each embedded scenario conforms to catalog.proto.

Every catalog file the test suites and fuzzers write is checked against catalog.proto too
(`CatalogProto`, called from `CheckpointRoundTrip`).

## Check the decoder

`check.mjs` runs the page's own decoder in Node (18 or later), with no browser. It reports any
file that fails to decode, has schema drift, holds a structural payload of a layout version the
page does not know, or has bytes outside every leaf node. It also prints how many of
catalog.proto's messages the files used.

```bash
node docs/format-explorer/check.mjs                      # the embedded scenarios
mvn test -Dtest=TestLocalCatalog -Dexplorer.dump=target/explorer-dump
node docs/format-explorer/check.mjs target/explorer-dump # every file the suite wrote
```

## Where record bytes go

`anatomy.mjs` decodes every Nth record of a log the contention driver captured
(`bench/results/captures/<label>-<hash>/log.bin`, `capture_log`) with the page's decoder and sums
the bytes of each leaf field by its schema path, its tag and length included; a map's entries are
split by key (`CompactSummary.extra{iceberg-version}`). It writes
`bench/results/anatomy/<capture>/`, which the lab reads as the source `anatomy`.

```bash
node docs/format-explorer/anatomy.mjs --every 50 bench/results/captures/cap-i1-*
```

## Files

- `index.html`: the explorer (HTML, CSS, JS and the embedded fixtures)
- `check.mjs`: the headless decoder check
- `anatomy.mjs`: record bytes by field, over a captured log
- `../../src/test/java/org/apache/iceberg/io/FormatExplorerFixtures.java`: the fixture generator
- `../../src/test/java/org/apache/iceberg/io/TestFormatExplorer.java`: the drift and freshness checks
- `../../src/test/java/org/apache/iceberg/io/CatalogProto.java`: the catalog.proto parser and
  conformance check
